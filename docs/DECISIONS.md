# 決定の記録

何を、なぜ、他にどんな選択肢があったかを残す。新しい決定は末尾に追加し、既存の決定を覆すときは新しい番号で追加して、古い方の状態を「置き換え（D-xxx）」にする。

- **状態**: `確定`（オーナーが決めた） / `採用`（AI の推奨案をそのまま採用。異論があれば変更）/ `置き換え`
- **決めた人**: オーナー / AI 提案 → オーナー承認 / AI 提案（推奨のまま採用） など。実験の振り返りのため、人間がどこで判断したかを残す

## D-018 ローダの作り: unreal モード、RAM ディスクは固定アドレス、カーネルは RAM ディスクから取り出す
- 日付: 2026-10-11 / 状態: 採用 / 決めた人: AI（Phase 1 の実装時）
- **決定**:
  - 1MB より上へのコピーには unreal モードを使う（`int 15h AH=87h` は使わない）
  - RAM ディスクは `0x400000` 固定。カーネルの上限は 3MB（`0x100000`〜`0x3FFFFF`）。E820 でこの範囲が使えることを確認し、使えなければ停止する
  - 先にフロッピー全体を RAM ディスクに読み、`KERNEL.SYS` は RAM ディスク上の FAT12 から取り出す
- **理由**: ディスクを 1 回なめるだけで済み、ローダの FAT12 処理が「メモリ上の構造をたどる」だけになる。固定アドレスなら E820 から置き場所を探す処理が要らない。8MB 以上のメモリがある前提（DESIGN.md §11.1）なら 4MB〜5.4MB は通常使える
- **代償**: 実機のフロッピーでは全トラックを読むので起動に 30 秒程度かかる見込み。必要になったら「FAT で使われている最後のクラスタまでだけ読む」最適化を入れる
- **検討した選択肢**: BIOS の拡張メモリ転送（`int 15h AH=87h`）、ローダが `KERNEL.SYS` だけを BIOS で読む方式

## D-019 ユーザプロセスとシステムコールの作り
- 日付: 2026-10-11 / 状態: 採用 / 決めた人: AI（Phase 9 の実装時）
- **決定**:
  - システムコールの入口はトラップゲート（割り込みを止めない）。キー入力など中で待つシステムコールがあるため
  - ユーザのポインタは使う前にページテーブルを引いて確かめる（ページフォルトから回復する仕組みは作らない）。単一 CPU で、確かめてから使うまでの間にページが消えることはない
  - ユーザモードの例外はそのプロセスだけを止める。Ctrl+C は「依頼」だけ割り込みで受け、ユーザモードへ戻る直前に止める
  - ELF ヘッダの解析は `xmas-elf`（DESIGN.md §3.4 で可としたもの）、配置と実行は自作
  - argv[0] は打った名前のまま渡す（Unix と同じ）
- **理由**: どれも単純さと安全さの釣り合い。ページフォルトからの回復は、例外の表と命令の位置の対応表が必要で大掛かりになる

## D-021 画面を 640x480 にし、320x200 も残す（起動時に選ぶ）
- 日付: 2026-10-11 / 状態: 確定 / 決めた人: オーナー（640x480 にする・320x200 を残す）、AI 提案 → オーナー承認待ち（切り替え方）
- **経緯**: AI がウィンドウシステムには 320x200 は狭いとして、640x480 への変更（D-002 の前提の変更）をオーナーに確認した。オーナーが 640x480 を選び、320x200 も残したいとして切り替え方を尋ねた
- **決定（切り替え方は AI の提案）**: 起動時に選ぶ。`BOOT.CFG` の `video=` で指定（既定 640x480）、起動中の Shift で一時的に 320x200、VESA で 640x480 にできなければ自動で 320x200
- **理由**: 動いている間の切り替えは VESA のモード設定に BIOS（リアルモード）が要り、プロテクトモードのカーネルから安全に呼べない（v8086 モードの仕組みが要る）。設定ファイルと Shift キーなら、実機で 640x480 が映らなくても戻せる
- **影響**: 320x200 用のアプリは 640x480 で 2 倍に表示する。D-002 の「画面はモード 13h」はこの決定で置き換え（320x200 は選べる形で残る）

## D-022 最低の CPU を 486 にする
- 日付: 2026-10-12 / 状態: 確定 / 決めた人: オーナー（AI が影響を調べて報告 → オーナーが「486 対応で進めて」）
- **経緯**: オーナーが「486 で起動するように修正するのは大変か」と尋ねた。AI が一時的に 486 向けにビルドして QEMU の 486 で起動を確かめ、変更が小さいことと実機での影響を報告した
- **決定**: ターゲットの CPU を i486 に（`targets/i486-vibeos.json`、64bit のアトミック操作も使わない）。ローダの確認を「486 以降（EFLAGS.AC）」に、カーネルは CPUID が無くても止まらない。テストはすべて `-cpu 486` で動かす
- **影響**: i686 の PC ではわずかに遅くなりうる（CMOV を使わない）。486 の実機では VESA 2.0 が無いことが多く 320x200 になり、シリアルマウスの機械ではマウスが使えない
- **対象外**: 386（Rust のロックが使う CMPXCHG・ページング関連の命令が無い）

## D-023 フロッピーを標準の FAT12 の配置にする（2nd ステージは LOADER.SYS）
- 日付: 2026-10-12 / 状態: 確定 / 決めた人: オーナー
- **経緯**: オーナーがイメージのダンプを見て、先頭に 2nd ステージが並び FAT やルートディレクトリが見当たらないので FAT になっていないのではと指摘した。AI が調べると `fsck.fat` は通る正しい FAT12 だったが、予約セクタが 64 で（D-011）、FAT は LBA 64 から始まっていた。Microsoft の仕様書は FAT12/16 の予約セクタを 1 にするよう勧めている。オーナーが「フロッピーは BPB を見ずに決め打ちでアクセスされることがあるので標準の形式に従う方がよい」と判断した
- **決定**: 予約セクタを 1 にし、`mkfs.fat` の 1.44MB と同じ配置にする（FAT は LBA 1、ルートディレクトリは LBA 19、データは LBA 33）。2nd ステージは `LOADER.SYS` というファイルにし、ブートセクタがルートディレクトリと FAT をたどって読む（DOS の IPL と同じ方式）
- **影響**: ブートセクタが FAT を解析するようになった（442 バイト）。`LOADER.SYS` を消すと起動しない。2nd ステージの上限は 32256 バイトのまま（`0x8000` から中継バッファ `0x10000` の手前まで）
- **検討した選択肢**: 予約セクタ 64 のまま（BPB を正しく読む OS では問題ない）/ 2nd ステージを連続したクラスタに置くことを前提にして先頭クラスタから続けて読む（ブートセクタは小さいが、他の OS でファイルを動かされると起動しない）

## D-024 ネットワークに着手する（ローカル優先・外部へのアクセスは確認まで禁止）
- 日付: 2026-10-12 / 状態: 確定 / 決めた人: オーナー（着手・ローカル優先・外部禁止）、AI（禁止の守り方）
- **経緯**: オーナーが「ネットワークの計画書を実装して。ローカルの機能を優先で実装し、外部へのアクセスは私が確認するまで禁止」と指示した。計画書（[plans/network.md](plans/network.md)）の「オーナーに決めてほしいこと」のうち、1（TCP/IP を自作）・2（最初のカードは ISA の NE2000）・4（非目標からネットワークを外す）は計画書の推奨どおりの実装の指示として扱った。3（実機で試す予定）は未回答
- **決定（外部へのアクセスを禁止する方法, AI）**:
  - QEMU のネットワークは slirp を `restrict=on` で使う（`make run` もテストも）。ゲストから外（インターネット・ホストの他のポート）へは出られず、使えるのは slirp の DHCP・ゲートウェイ 10.0.2.2 への ping・明示したポート転送だけ。restrict=on の slirp は DHCP でゲートウェイと DNS を知らせない
  - DNS・NTP のサーバの既定値を持たない（BOOT.CFG の `dns=`・`ntp=` か DHCP で来たものだけ）。外のサーバ（pool.ntp.org など）を書き込まない
  - テストの DNS・NTP・HTTP はすべてテストランナーがホストの中で答える（D-025）
  - 作業中に AI もインターネットにつながない（新しい外部クレートを追加しない・Web を見ない）
- **解除するとき**: オーナーの確認の後、`make run` の `restrict=on` を外す（または別のターゲットにする）だけで外につながる。DNS は slirp の 10.0.2.3 を `dns=` に書く

## D-025 ネットワークのテストの組み立て（QEMU のハブ + slirp + テストランナーの偽のホスト）
- 日付: 2026-10-12 / 状態: 採用 / 決めた人: AI（推奨のまま採用）
- **決定**: QEMU の中にハブを作り、ゲストのカード・slirp（restrict=on）・テストランナー（UNIX ドメインのデータグラムで Ethernet のフレームをやり取り）をつなぐ
  - テストランナーはハブを流れるフレームをすべて記録し（OUT/NAME.pcap）、自分で解析して確かめる（`expect-packet`。チェックサムの誤りがあれば失敗）。解析はゲストの vibe-net とは別に書いた（同じ間違いを見逃さないため）
  - テストランナーは 10.0.2.50 の「偽のホスト」として ARP・ping・DNS・NTP に答える。restrict=on の slirp は UDP を外へ通さないので、DNS と NTP はこちらで答える必要がある
  - HTTP（ゲスト → ホスト）は slirp の guestfwd で 10.0.2.100:80 への接続ごとにテストランナーを `http-serve` として起動する。ホスト → ゲストの httpd は hostfwd
- **理由**: 外に出ずに、TCP の相手には本物の TCP（slirp）を使える。UDP の相手と記録は自分で持つので、外の状況でテストが揺れない
- **検討した選択肢**: slirp を制限なしで使う（DNS・NTP は slirp 経由で本物に届いてしまう。D-024 に反する）/ テストランナーが TCP まで全部答える（TCP を 2 つ書くことになり、相手の正しさも怪しくなる）/ QEMU の filter-dump で記録する（記録はできるが答えられない）

## D-026 TCP の受信の窓をカードの受信バッファに合わせて小さくする

## D-029 LAN へのアクセスを許し、WAN は許可制にする（WAN のガード）

## D-043 アプリの ELF をページの境目にそろえない（-n）。圧縮率のテストは詰め物の無い ELF に対して 60% 以下で見る
- 日付: 2026-10-12 / 状態: 採用（オーナーに報告し、確認された: D-067） / 決めた人: AI
- **経緯**: パイプの P3 でアプリを 15 本足したところ（36 本）、カーネルとアプリを圧縮しないイメージ（`make COMPRESS=0`、テストの `vibeos-raw.img`）がフロッピーに入らなくなった（約 85KB 足りない）。アプリの ELF は、ファイルの中でもセグメントをページの境目（4KB）にそろえていて、1 本あたり 5KB ほどが詰め物の 0 だった
- **決定**:
  - アプリをリンクするときに `-n`（nmagic）を付け、ファイルの中ではそろえない（`apps/.cargo/config.toml`）。カーネルはセグメントを番地へ写すだけなので、ファイルの位置と番地がページの中でそろっている必要は無い。メモリの中の並び（コードとデータを別のページ）は変わらない
  - 圧縮しないアプリの合計は 1,007,888 → 756,512 バイト（`sort` を標準の `sort_by` から小さなマージソートにした分も含む）。圧縮しないイメージの空きは 157,696 バイト
  - gzip した大きさは変わらない（Phase 30 のアプリ 16 本で 175,775 → 175,312）が、元から詰め物が無くなったので率は上がる（43.8% → 57.8%）。`make test-apps-gz` の率の上限は、詰め物の無い ELF に対して、Phase 30 のアプリも全部のアプリも 60% にした（D-037 の 45%・50% は詰め物込みの値）
- **他の選択肢**: 圧縮しないイメージに入れるアプリを減らす（`COMPRESS=0` の意味が変わる）、アプリを `opt-level = "s"` にする（速さが落ち、率はほとんど変わらない）、率の上限を 45% のままにして詰め物込みの大きさを別に計算する（実物と違う数で見ることになる）

## D-048 画面モードの選び方の細かいところと、そのテストの仕方（M1）
- 日付: 2026-10-13 / 状態: 採用（オーナーに報告する） / 決めた人: AI（EDID のテストの前提はオーナー）
- **経緯**: オーナーが「QEMU は EDID を読み出せないはずなので、その想定でテストして」と指示した。M1 で試すと、QEMU 11.1 の `-vga std` は VBE の `4F15h` に答えて EDID を返した（既定の本来の解像度は 1280x800）
- **決定**:
  - EDID が無いときの動き（1024x768 まで）は、QEMU の `-global VGA.edid=off` で EDID を消して確かめる（オーナーの想定どおりの場合）。EDID があるときの動きも `-global VGA.xres=1600 -global VGA.yres=1200` で確かめる（`62-video-edid`）
  - `video=WxH` はモニタ（EDID）と既定の 1024x768 の代わりになる上限で、メモリの上限（画面 1 枚が RAM の 1/8）は超えない（大きな画面を頼んでメモリが足りなくなるのを避けるため）
  - 製品の `BOOT.CFG` は `video=auto` にした。`video=` は行の頭のものだけを読む（前のローダは BOOT.CFG のどこでも探していて、コメントの `# video=640x480 or video=320x200` に一致していた）
  - シナリオの画面の大きさをそろえるため、テストランナーは BOOT.CFG に `video=` を書かないシナリオを `video=640x480` で起動する（期待画像と座標を 640x480 のまま使える）
  - デスクトップで独自のパレットを持つウィンドウ（`view` の 8 ビットの画像など）は、標準のパレットの近い色に置き換えず、その色のまま出す（32 ビットの画面になったので）
  - Bochs（`make test-bochs`）はレトロ（320x200）で動く。Debian の Bochs 2.7 の VGA BIOS（`VGABIOS-lgpl-latest`）はモード一覧に 640x480 までの 8 ビットのモードしか出さない（QEMU の SeaVGABIOS `vgabios-stdvga.bin` に替えると Bochs の VBE を見つけられず、標準の VGA のモードだけになった）。Bochs のテストは画面を比べないので、レトロでシナリオが通ればよいことにする
- **他の選択肢**: QEMU の EDID を使わずに EDID の処理を確かめない（読めるのに試さない理由が無い）。`video=` でメモリの上限も超えられるようにする（メモリの少ない機械で起動できなくなるおそれ）

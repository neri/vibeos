# 計画書: アプリの圧縮（gzip / deflate）

状態: **完了（2026-10-12。結果は §9）。PLAN.md の Phase 30〜31** / 作成: 2026-10-12 / 作成者: AI / 方針の決定: オーナー（2026-10-12「推奨で計画書を作って」, DECISIONS.md D-035）

フロッピーの `/BIN/*.ELF` を gzip（deflate）で圧縮して置き、カーネルが起動するときに展開してから ELF として読む。カーネルの圧縮（[plans/compress.md](compress.md)）とは別の計画。

## 1. 背景と測定（2026-10-12）

カーネルは「ローダが展開できればよく、展開が簡単なこと」を優先して LZSA2 にした（D-034）。アプリはカーネルが展開するので、ヒープが使え、展開の制約がほとんど無い。LZSA に拘る理由は「もう作ってある」ことだけで、率も deflate と変わらない。メジャーな形式なら、ホストの `zcat`・`gzip -l` で中身を確かめられ、仕様（RFC 1951・1952）も整っている（オーナーの指摘）。

アプリ 16 本（元 372,352 バイト）を 1 本ずつ圧縮した合計:

| 形式 | 辞書なし | 共有辞書 32KB あり（辞書の大きさ込み） | カーネル側の展開器 |
|---|---|---|---|
| **deflate（gzip -9）** | **160,623（43.1%）** | 約 110,500（29.7%） | `miniz_oxide`（DESIGN.md §3.4 で可としたもの） |
| zstd -19 | 155,525（41.8%） | 約 83,400（22.4%） | `ruzstd`（§3.4 に無い。コードも大きい） |
| LZMA2 -9e（xz） | 148,056（39.8%） | xz の形式に辞書の仕組みが無い | no_std のクレートが見当たらない |
| LZSA2（自作） | 161,780（43.4%） | 圧縮器に辞書の対応が要る | 既にある |

- 辞書なしでは形式による差は小さい（40〜43%）。大きく効くのは共有辞書（アプリはどれも vibe-rt の同じコードを含む）で、それは後の段階の候補にする（§8）
- 辞書は `zstd --train` で作ったもの。辞書の大きさは圧縮後（gzip -9 で 17,379、zstd で 16,707）

## 2. ゴール

- `/BIN/*.ELF` は gzip で圧縮した形で置く。名前は `.ELF` のまま（§6）
- カーネルの `process::spawn` は、ファイルの先頭が gzip の印（`1F 8B`）なら展開してから ELF として読む。印が無ければ今どおり ELF として読む（ホストから圧縮せずに入れたアプリも動く）
- 壊れた gzip（CRC32・大きさが合わない、途中で切れている）は `ENOEXEC` で、カーネルは落ちない
- `make COMPRESS=0` ではアプリも圧縮しない（カーネルと同じ切り替え）
- ホストでは `zcat` でそのまま元の ELF が取り出せる

**やらないこと**:
- 共有の辞書（§8 の候補。この計画の結果を見てから決める）
- zstd・LZMA など deflate 以外の形式
- 展開にかかる時間の測定・上限（カーネルの圧縮と同じく測らない。D-034）
- アプリ以外のファイル（画像・テキスト）の圧縮、ファイルシステムでの透過的な圧縮
- アプリのリンクのしかたの変更（ページ境界の詰め物を減らすなど）。§8 の候補

## 3. 設計の要点

### 3.1 ファイルの形: gzip（RFC 1952）

```
1F 8B 08 FLG MTIME(4) XFL OS [FEXTRA][FNAME][FCOMMENT][FHCRC] deflate のデータ CRC32(4) ISIZE(4)
```

- ホストの `gzip -9 -n`（名前と時刻を入れない。同じ入力なら同じイメージになるように）で作る
- 中の deflate（RFC 1951）は `miniz_oxide` で展開する。gzip の枠（ヘッダの読み飛ばし・CRC32・ISIZE の確認）は自作する（数十行。CRC32 は `vibe-pack` のものを使う）
- 展開後の大きさは末尾の ISIZE で分かるので、先にその大きさの出力先を取る。ISIZE はユーザ空間の上限（`USER_STACK_TOP - USER_BASE`）を越えたら `ENOEXEC`（大きすぎる値で大きなメモリを取らない）
- 他の案: zlib 形式（RFC 1950）。辞書の仕組み（FDICT）があり §8 の辞書に向くが、ホストの `zcat` では開けない。辞書を入れる段階で zlib に切り替える（印で見分けられるので、両方を読めるようにすればよい）

### 3.2 置き場所

| もの | 置き場所 | 中身 |
|---|---|---|
| gzip の枠と展開 | `crates/vibe-pack` に `gzip` モジュールを足す | `gunzip(src) -> Result<Vec<u8>, GzipError>`: ヘッダを読み、`miniz_oxide` で ISIZE の大きさの出力先へ展開し、CRC32 と大きさを確かめる。`no_std` + `alloc`。ホストで `cargo test` |
| カーネル | `kernel/src/process.rs` の `spawn` | `fs::read_file` の後、先頭が `1F 8B` なら `vibe_pack::gzip::gunzip` してから今までの ELF の読み込みへ。失敗は `ENOEXEC`、メモリが足りなければ `ENOMEM` |
| ビルド | Makefile | `$(APPS_DIR)/BIN/*.ELF`（今の strip 済みの ELF）から `build/rootfs-apps-gz/BIN/*.ELF` を `gzip -9 -n -c` で作り、`COMPRESS=1` ならそちらをイメージに入れる |

- カーネルの `vibe-pack` の依存は今 `qemu-test` のときだけ（D-034）。通常の依存に戻す（`miniz_oxide` も引き込む）
- `miniz_oxide` は `default-features = false` で、`with-alloc` だけを使う（カーネルでは FPU/SSE を使わない決まりがあるので、`simd` などの feature は入れない）。追加したら LOG.md の「追加した外部クレート」に書く
- カーネルの大きさは inflate の分（見込み 10〜20KB）増えるが、カーネル自体を圧縮しているのでフロッピーへの影響は小さい

### 3.3 メモリ

- 展開している間は「読んだファイル（圧縮後）」と「展開後」の両方をヒープに持つ。今いちばん大きい `EDIT.ELF` で 23KB + 45KB。最低動作メモリ（8MB）で問題にならない
- `miniz_oxide` の展開の状態（約 11KB）はヒープから取り、展開が終われば返す

## 5. テストの方法

- **ホスト**: `crates/vibe-pack` の `cargo test`（A1）。テストの gzip はテストの中で作る（`miniz_oxide` の圧縮 + 自分で組んだヘッダ）ので、ホストの `gzip` コマンドに頼らない
- **ビルド**: `make test` の中で、イメージから `/BIN/*.ELF` を `mcopy` で取り出して `zcat` し、`$(APPS_DIR)` の元の ELF と `cmp` する（ホストの `gzip` との互換をここで確かめる）
- **カーネル**: 今のシナリオがアプリをすべて動かしているので、それが通ることが「展開できる」ことの確認になる。加えて ktest で、壊れた gzip（CRC32 を書き換えたもの・途中で切ったもの）と圧縮していない ELF を `fs::write_file` で RAM ディスクに書いて `spawn` する
- **ネットワークのシナリオ**: `36-net-httpd` などはフロッピーの `/BIN/EDIT.ELF` をそのまま送り、テストランナーもイメージの中のファイルと比べるので、圧縮したファイルのまま一致する（変更は要らない見込み）

## 6. オーナーに決めてほしいこと（2026-10-12 すべて推奨どおりに決定）

決定済み（2026-10-12, オーナー「推奨で計画書を作って」, D-035）: 形式は deflate（gzip）、カーネル側の展開器は `miniz_oxide`、共有の辞書は最初の計画に入れない。

残っている問い:

1. **ファイルの名前**: 推奨は `.ELF` のまま（中身の印で見分ける。シェルの起動のしかた・パスの決め方が変わらない）。もう 1 つは拡張子を変える（例: `.ELZ`）方法で、ホストから見て圧縮していると分かりやすいが、シェルとパスの決め方を変えることになる
2. **ホストの圧縮のツール**: 推奨は `gzip -9 -n`（どこにでもある）。`zopfli`（同じ deflate を時間をかけてより小さくする。一般に数 % 縮む）を使う方法もあるが、ホストのツールかクレートが増える。まず `gzip` で作り、結果を見てから考える
3. **`COMPRESS=0` でアプリも圧縮しないか**: 推奨は「カーネルと一緒に切り替える」（切り分けのため）

## 7. 心配な点

- **`miniz_oxide` の no_std での使い方**: `with-alloc` で `Vec` を使う API と、出力先を渡す API がある。ISIZE の大きさの出力先を先に取り、それを越えて展開しようとしたら壊れているとして止める（大きな出力でメモリを使い切らない）
- **起動の速さ**: 展開の分だけアプリの起動が遅くなるが、486 でも数十 KB の inflate は短い見込み（測らない。D-034 と同じ考え）
- **ホストから入れたアプリ**: 印で見分けるので、圧縮していない ELF も今どおり動く。逆に、`gzip` で圧縮したテキストファイルなどを実行しようとした場合は、展開した後の ELF の確認で `ENOEXEC` になる
- **`fsck.fat`・mtools**: ファイルの中身が変わるだけなので影響しない

## 8. 別の計画の候補（この計画には入れない）

- **共有の辞書**: zlib 形式の FDICT で、vibe-rt の共通部分から作った辞書（32KB まで）を `/BIN/APPS.DIC` などに置く。測定ではアプリの合計が 43.1% → 29.7%（辞書込み）。辞書を消すと全部のアプリが動かなくなる・アプリを足したら辞書を作り直すか、という弱さがある。zstd + 辞書（22.4%）を比べ直すのもこのとき
- **ELF の詰め物を減らす**: アプリはページ境界（4KB）にそろえた詰め物を含む。リンクのしかたで減らせるが、圧縮すれば 0 の並びはほとんど縮むので効き目は小さい見込み
- **vibe-rt を共有ライブラリにする**: 重なりそのものを無くす方法。圧縮より根本的だが、動的リンクの仕組みが要る大きな変更

## 9. 結果（2026-10-12）

| | 元 | 圧縮後 | 比 |
|---|---|---|---|
| アプリ 16 本（`/BIN/*.ELF`） | 372,352 | 160,732 | 43.1% |
| カーネル（`miniz_oxide` の inflate の分だけ増えた） | 308,528 → 324,624 | 135,173 → 144,182 | 44.4% |
| フロッピーの空き | 819,200（カーネルだけ圧縮） | 1,021,952 | |

- 既存のシナリオ（アプリを動かすもの全部。8MB の `20-low-memory` を含む）が圧縮したアプリで通った。Bochs でも `05-ktest`・`14-user-process`・`42-kernel-uncompressed` が通った
- ktest `process_runs_gzip_and_plain_elf`: 圧縮していない ELF が動く。CRC32・中身を壊したもの、途中で切ったもの、ISIZE がユーザ空間より大きいものは `ENOEXEC`。ISIZE が 2GB 近いものは出力先を取れず `ENOMEM`（ヒープは連続したページを一度に取るので、取れなかった分は残らない）
- `make test-apps-gz`: イメージの `/BIN/*.ELF` をすべて `zcat` して元の ELF と一致した（ホストの `gzip` との互換）
- `42-kernel-uncompressed` のイメージ（`COMPRESS=0` と同じ中身）はアプリも圧縮せず、その中で `hello` が動く
- 展開の状態（約 11KB）は `Box` でヒープに取る（`miniz_oxide` の `decompress_slice_iter_to_slice` はスタックに置くので使わない）

# 計画書: ネットワーク対応

状態: **実装済み（Phase 16〜21）。LAN・WAN とも制限なく使える（D-032）。WAN のテストの宛先はオーナーの許可制** / 作成: 2026-10-12 / 作成者: AI

> 2026-10-12 オーナーの指示で着手し、N1〜N6 を実装した（PLAN.md の Phase 16〜21、DECISIONS.md D-024〜D-028）。
> この計画書との違い: テストの DNS・NTP は slirp の外のサーバではなくテストランナーが答える（restrict=on の slirp は UDP を外へ通さないため, D-025）。
> Bochs（Debian の 2.7）には slirp が無いので、Bochs の中だけの vnet で DHCP・ARP・ping を確かめた（get は vnet に HTTP が無いので QEMU だけ）。
> §6 の 3（実機のカード）はオーナーの回答で未定（2026-10-12）。N6 では RTL8139 まで作った。時差は当面 JST（D-028）。

VibeOS から LAN とインターネットにつなぎ、`ping`・名前解決・時刻合わせ・HTTP でのファイルの取得と公開ができるようにする。
ドライバと TCP/IP は自作する（DESIGN.md §3.4 の「OS の仕組みそのもの」に当たるため）。

## 1. ゴール

- 起動すると DHCP でアドレスをもらい、ステータスバーに IP アドレスが出る
- シェルから `ping 10.0.2.2`、`host example.com`、`get http://…/file.txt`（ファイルに保存）が使える
- `httpd` を動かすと、ホストのブラウザからフロッピーのファイルが見える
- 時刻を NTP（SNTP）で合わせられる
- すべての段階を QEMU の自動テストで確かめる（インターネットにはつながない。§5）

**やらないこと**: IPv6, IP のフラグメントの組み立て, TCP の高度な輻輳制御（SACK・ウィンドウスケール）, TLS（HTTPS）, 無線, ルータ機能

## 2. ハードウェア

| 候補 | バス | 長所 | 短所 |
|---|---|---|---|
| **NE2000（推奨・最初）** | ISA | 486 の時代の定番。ポート I/O だけで書ける。QEMU（`ne2k_isa`）・Bochs（`ne2k`）の両方にある | 遅い（PIO）。実機ではジャンパや PnP で I/O ポートと IRQ を合わせる必要がある |
| NE2000 PCI | PCI | ドライバは NE2000 と共通。PCI の列挙を覚える足がかり | PCI のバスの列挙（コンフィグ空間）を書く必要がある |
| RTL8139 | PCI | 実機で入手しやすい。DMA で速い | 新しいドライバを 1 つ書く |

最初は NE2000（ISA, I/O ポート 0x300, IRQ 9 または 10）。I/O ポートと IRQ は `BOOT.CFG` で変えられるようにし（例: `net=ne2000,0x300,10`）、起動時にカードのリセットと MAC アドレスの PROM の読み出しで有無を確かめる。PCI 対応は最後の任意の段階（N6）にする。

## 3. 設計の要点

### 3.1 層の分け方

```
アプリ（ping, host, get, httpd, ntp）── vibe-rt::net（ソケットの薄いラッパ）
──────── システムコール（ソケット）────────
カーネル: net スレッド ─ ソケット表・タイマ
          vibe-net（ハードウェアに依存しない TCP/IP。ホストでテストする）
          drivers/ne2000.rs（送受信・割り込み）
```

- **`crates/vibe-net`**（新規、`no_std` + `alloc`）: Ethernet / ARP / IPv4 / ICMP / UDP / TCP / DHCP / DNS の組み立てと解析、チェックサム、ARP の表、TCP の状態遷移。「フレームを受け取る」「送るフレームを取り出す」「時刻を進める」だけの API にして、ハードウェアと時計を持たない。ホストの `cargo test` で、記録したパケット・2 つのスタックを直結した通信・**わざとパケットを落とす回線**（再送の確認）を試す
- **ドライバ**: 割り込みハンドラは受信したフレームを固定長のリングに積んで net スレッドを起こすだけ（DESIGN.md §6.4 の約束どおり、中でメモリを確保しない）
- **net スレッド**（カーネルスレッド）: 受信の処理・TCP の再送タイマ・ARP の再送をまとめて行う。ソケットで待つプロセスは `WaitQueue` で起こす
- **ソケット**: ファイルと同じ番号（fd）の表に入れ、`read` / `write` / `close` をそのまま使えるようにする。追加するシステムコールは `socket`, `connect`, `bind`, `listen`, `accept`, `sendto`, `recvfrom`, `net_info`（アドレスなどの取得）程度
- **設定**: 既定は DHCP。`BOOT.CFG` で固定アドレスも指定できる（`ip=10.0.2.15/24 gw=10.0.2.2 dns=10.0.2.3`）。テスト用に DNS・NTP サーバのポートも指定できるようにする（§5）

### 3.2 アプリとコマンド

| 名前 | 中身 |
|---|---|
| `net`（シェル） | MAC・IP・ゲートウェイ・DNS・送受信の数を表示 |
| `ping HOST` | ICMP エコー。往復時間を表示、Ctrl+C で止めて集計 |
| `host NAME` | DNS で A レコードを引く |
| `ntp [HOST]` | SNTP で時刻を合わせ、CMOS の時計にも書く |
| `get URL [FILE]` | HTTP/1.0 の GET。ファイルに保存（進み具合を表示） |
| `httpd [PORT]` | フロッピーのファイルを HTTP で返す（ディレクトリは一覧の HTML） |

## 4. 段階（Phase）と完了条件

番号は着手順が決まってから PLAN.md の Phase 番号に割り当てる。

| 段階 | 内容 | 完了条件（自動で確かめる） |
|---|---|---|
| N1 | NE2000 ドライバ, Ethernet の送受信, ARP（問い合わせ・応答・表） | QEMU で起動するとシリアルに MAC アドレスが出る。ゲートウェイ（10.0.2.2）の MAC を ARP で引ける。パケットの記録（pcap）に正しい ARP が残る |
| N2 | IPv4, ICMP, `ping`, 固定アドレス | `ping 10.0.2.2` に応答が返る。ホストのテストでチェックサム・解析が通る |
| N3 | UDP, ソケットのシステムコール, DHCP, DNS, SNTP | DHCP で 10.0.2.15 がもらえ、ステータスバーに出る。テストランナーが立てた DNS・NTP サーバに `host`・`ntp` が問い合わせ、結果（アドレス・時刻）が合う |
| N4 | TCP（クライアント）, `get` | テストランナーが立てた HTTP サーバから 100KB 程度のファイルを取り、ホスト側で中身が一致する（mtools で取り出して比べる）。ホストのテストで、パケットを落とす回線でも転送が完了する |
| N5 | TCP（サーバ）, `httpd` | QEMU のポート転送を通して、テストランナーがフロッピーのファイルを HTTP で取得でき、中身が一致する。同時に 2 本つないでも動く |
| N6（任意） | PCI のバスの列挙, NE2000 PCI（余力があれば RTL8139） | `ne2k_pci` の QEMU で N2〜N5 のシナリオが通る。`pci` コマンドで機器の一覧が出る |

N1〜N5 は Bochs（`ne2k` + slirp）でも `ping` と `get` のシナリオを流す。

## 5. テストの方法

- QEMU は `-netdev user`（slirp）で外とつなぐ。ゲストから見た 10.0.2.2 はホストのループバックなので、**テストランナー（`vibe-run`）がホストに立てたサーバに、ゲストから 10.0.2.2:ポート でつながる**
- テストランナーにシナリオの命令を足す（案）
  - `net` … ネットワークカードを付けて起動する（付けないシナリオは今までどおり）
  - `serve-http DIR PORT`, `serve-dns PORT NAME=ADDR…`, `serve-ntp PORT TIME` … ホスト側に小さなサーバを立てる
  - `host-fetch URL FILE` … ゲストの `httpd` からホストが取得して比べる（`hostfwd` を使う）
  - `pcap FILE` … QEMU の `filter-dump` でパケットを記録し、`expect-pcap` で中身を確かめる
- インターネット（本物の DNS や Web サイト）にはつながない。テストが外の状況で揺れないようにするため。手で試すときは slirp の DNS（10.0.2.3）を使えば本物の名前も引ける

## 6. オーナーに決めてほしいこと

1. **TCP/IP を自作するか**: 推奨は自作。外部クレート（`smoltcp`）を使えば早いが、「外したら仕組みを説明できなくなる」部分そのものなので DESIGN.md §3.4 の基準では自作になる
2. **最初のカードを NE2000（ISA）にするか**: 推奨は NE2000。PCI は N6 で任意
3. **実機で試す予定があるか**: あるなら、そのカード（ISA の NE2000 互換か、PCI の RTL8139 か）を N6 の前に優先する
4. DESIGN.md の「非目標」からネットワークを外すこと（着手が決まったら、決めた人を付けて DECISIONS.md に残す）

## 7. 心配な点

- **TCP が一番重い**: 状態遷移・再送・順番の入れ替わり・接続の終わり方で不具合が出やすい。ホストのテストで、パケットを落とす・順番を変える回線を作って先に潰す
- **フロッピーの空き**: 今の空きは約 840KB。カーネルは数十 KB、アプリは 1 本 20〜40KB 増える見込みで足りるが、デスクトップの計画と合わせて見積もり直す
- **ISA カードの割り込みの共有**: IRQ 9 / 10 は空いていることが多いが、実機では衝突しうる。設定で変えられるようにし、応答が無ければ表示して諦める（ハングしない）
- **slirp の癖**: ICMP はゲートウェイ（10.0.2.2）宛てだけ応答する、などの制約がある。テストはその範囲で書く

# 計画書: LZSA の圧縮器・展開器を自作し、本家の圧縮率をどこまで再現できるか確かめる

状態: **完了（2026-10-12。結果は §8）**。PLAN.md の Phase 22〜26 / 作成: 2026-10-12 / 作成者: AI

カーネルとアプリを圧縮するときの形式の第一候補として LZSA を調べた（DECISIONS.md D-033）。ここでは圧縮器と展開器を Rust で自作し、本家の `lzsa` コマンドと比べて圧縮率をどこまで再現できるかを確かめる。カーネルやアプリへの組み込みはこの計画に入れず、結果を見てから別の計画にする。

## 1. 背景（2026-10-12 の測定）

本家の `lzsa` v1.4.1（commit `15ee2df`）で測った値。

| 対象 | 元 | LZ4 -12 | 本家 LZSA1 | 本家 LZSA2 | gzip -9 | xz -9e |
|---|---|---|---|---|---|---|
| kernel.sys | 308,528 | 167,884 | 160,062 | 142,873 | 149,766 | 127,259 |
| kernel.sys + BCJ | 308,528 | 157,559 | 150,426 | 135,373 | 140,685 | 119,541 |
| アプリ 16 本（1 本ずつ圧縮した合計） | 372,352 | 190,997 | 178,877 | 161,457 | 160,884 | 148,056 |

- x86 用の展開ルーチン（本家の 32 ビット小型版）は LZSA1 が 96 バイト、LZSA2 が 187 バイト
- 本家の圧縮器は C で約 7,000 行（`libdivsufsort` 込み）。最適パース（全体で一番短くなる区切り方を探す処理）と、LZSA2 の rep-match（前回と同じオフセットの再利用）を考えた探索で率を出している

## 2. ゴール

- `crates/vibe-lzsa` に、LZSA1・LZSA2 の展開器と圧縮器がある。ストリーム形式（64KB ごとのフレーム）とブロック単体の形式（raw block）の両方を扱う
- 自作の圧縮器が出したデータを、**本家の `lzsa -d` で展開できる**（実装中のテスト）
- 本家が出したデータを自作の展開器で展開できる（実装中のテスト）
- 自作の圧縮器の出力の大きさを本家と比べ、どこまで近づいたかを記録する
- 最後は本家のツールが無くても、自作の圧縮器と展開器だけでテストが通る（最終のテスト）

**やらないこと**:
- カーネル・ローダ・アプリのローダへの組み込み（別の計画）
- x86 のアセンブラの展開ルーチン
- BCJ フィルタ（組み込むときの計画で扱う）
- 本家の辞書（`-D`）、逆向きの圧縮（`-b`）、最短の一致長の変更（`-m`）

## 3. 設計の要点

### 3.1 置き場所

| もの | 置き場所 | 中身 |
|---|---|---|
| 形式・展開・圧縮 | `crates/vibe-lzsa`（新規） | 展開器は `no_std` で、ヒープを使わない（出力先の `&mut [u8]` に書く）。いずれカーネルやローダの Rust スタブでも使えるようにするため。圧縮器は `alloc` の feature の中に置く（ホストでしか使わない） |
| コマンド | `tools/vibe-lzsa`（新規） | `vibe-lzsa -f1|-f2 [-r] IN OUT`（圧縮）、`-d`（展開）、`bench`（本家との比較表）。本家と同じ形で呼べるようにして、テストのスクリプトで入れ替えられるようにする |
| 本家のツール | `build/ext/lzsa/`（コミットしない） | `make lzsa-ref` で GitHub から commit `15ee2df` を取ってきてビルドする。実装中だけ使う |

- 実装は仕様書（本家の `BlockFormat_LZSA1.md`, `BlockFormat_LZSA2.md`, `StreamFormat.md`）から書き、本家のコードは写さない。探索の工夫は README などで考え方を調べ、自分で組み立てる
- 外部クレートは使わない（テスト用の乱数も自作の小さな擬似乱数で足りる）

### 3.2 展開器

- 1 つのコマンドを読む → リテラルを写す → 一致を写す、を繰り返すだけ。LZSA2 はニブル（4 ビット）を読む状態を 1 つ持つ
- オフセットは負の数で入っている。一致は前に書いた出力から写す（重なってよい。1 バイトずつ写す）
- 壊れたデータで panic しない。入力の終わりを越える読み込み・出力の先頭より前を指すオフセット・出力先が足りない場合はエラーを返す

### 3.3 圧縮器（段階的に率を上げる）

| 段階 | 一致の探し方 | 区切り方 | 見込み |
|---|---|---|---|
| 貪欲 | ハッシュチェーンで一番長い一致 | 見つけたら使う | 本家より 1 割前後大きい |
| 遅延評価 | 同上 | 1 つ先の位置の一致が長ければリテラルにする（zlib と同じ） | 数 % 縮む |
| 最適パース | 各位置の一致の候補（長さごとの一番近いオフセット）を集める | 後ろから DP で、各位置からブロックの終わりまでの最短のビット数を求める | LZSA1 は本家にかなり近づく見込み |
| rep-match を考える最適パース（LZSA2） | 同上 + 「前回のオフセット」で一致する長さ | 前から DP し、各位置で「前回のオフセット」ごとに上位 K 個の候補を残す | LZSA2 で本家に近づくのに必要 |

- 大きさはビット単位で数える（LZSA2 はニブルがあるため）。トークン 8、ニブル 4、バイト 8
- ブロックは 64KB ごと。前のブロックを辞書として参照できる（最大オフセット 65535）
- 圧縮の速さの目安: kernel.sys（約 300KB）を release ビルドで 10 秒以内

## 5. テストの方法

### 5.1 比べる対象のファイル

- そのときのビルドの `kernel.sys` と `/BIN` のアプリ全部（`build/` から集める。ビルドのたびに中身が変わるので、率は「自作 ÷ 本家」の比で見る）
- 決まった形の小さいファイル（テストの中で作る）: 空、1 バイト、2〜3 バイト（最短の一致長の境目）、同じバイトの繰り返し（長い一致・長さの拡張）、乱数（圧縮できない）、64KB ちょうど・64KB + 1・200KB（ブロックの境目とブロックをまたぐ参照）、オフセットの境目（32・512・8704 など LZSA2 のオフセットの形が変わる所）、長さの拡張の境目（リテラル 7・256・LZSA2 の 18・ほか）
- 擬似乱数で作った「一部が繰り返す」データ（種を固定して 100 通りほど）

### 5.2 実装中（Z1〜Z4）: 本家と互換かを確かめる

`make test-lzsa`（`make test` から呼ぶ）で、§5.1 のファイルと形式（LZSA1/2 × ストリーム/raw block）のすべての組み合わせについて次を確かめる。

1. 自作で圧縮 → **本家の `lzsa -d` で展開** → 元と一致
2. 自作で圧縮 → 自作で展開 → 元と一致
3. 本家で圧縮 → 自作で展開 → 元と一致
4. 自作と本家の大きさを表にして出す（失敗にはしない）

### 5.3 最終（Z5 以降）: 本家に頼らない

- `crates/vibe-lzsa` の `cargo test`: §5.1 の決まった形のファイルと擬似乱数のデータで、自作で圧縮 → 自作で展開 → 元と一致
- `make test` の中で、そのときの `kernel.sys` とアプリ全部を `tools/vibe-lzsa` で圧縮 → 展開 → `cmp` で一致
- 壊れたデータ（途中で切る・バイトを書き換える）を展開して panic しないこと
- 本家のツール・本家が出したデータには頼らない

## 7. 心配な点

- **LZSA2 の最適パースは難しい**: rep-match があるので「その位置まで来たときの前回のオフセット」で後の大きさが変わり、単純な DP では最短にならない。Z4 で詰まる可能性がいちばん高い。届かなければ差を記録して終える
- **本家と同じ出力にはならない**: 区切り方が違ってもデータとして正しければよい。本家とバイト単位で同じことは求めない
- **ストリーム形式の細かい所**: 圧縮できないブロックを「無圧縮」（フレームの U ビット）で入れるかなど、仕様書にはっきり書いていない所がある。本家の `lzsa -d` で展開できるかを Z2 で確かめながら決める
- **raw block は 64KB まで**: kernel.sys はストリーム形式で扱う。raw block は小さいファイルとアプリ（どれも 64KB 未満）だけ

## 8. 結果（2026-10-12）

**目標に届いた**: 合計の大きさで LZSA1 は本家の 100.11%、LZSA2 は 100.00%（本家より 6 バイト小さい）。kernel.sys の LZSA2 は本家より 329 バイト小さい。

比べた対象は kernel.sys とアプリ 16 本（合計 680,880 バイト、ストリーム形式）。

| 区切り方 | LZSA1 | 本家との比 | LZSA2 | 本家との比 |
|---|---|---|---|---|
| 本家 `lzsa` v1.4.1 | 338,939 | 100% | 304,330 | 100% |
| 貪欲（Greedy） | 356,579 | 105.20% | 354,819 | 116.59% |
| 遅延評価（Lazy） | 344,836 | 101.74% | 330,851 | 108.71% |
| 最適パース（Optimal、rep-match を考えない） | 339,310 | 100.11% | 314,629 | 103.38% |
| rep-match を考えた最適パース（OptimalRep、既定） | 339,310 | 100.11% | **304,324** | **100.00%** |

- 本家との互換: 自作で圧縮 → 本家の `lzsa -d` で展開、本家で圧縮 → 自作で展開、自作同士の往復を、実物 17 本と境目のデータ・擬似乱数のデータ 167 個 × LZSA1/2 × ストリーム/raw block × 4 つの区切り方で 6,318 通り確かめ、すべて一致した（`make test-lzsa-ref`）
- 圧縮の速さ: kernel.sys の LZSA2（既定の設定）が 2.2 秒（本家 0.55 秒）。目標の 10 秒以内
- 効いたこと:
  - 一致の候補を探す深さ（256 → 4096 で LZSA1 は 100.69% → 100.11%、LZSA2 は 0.3% 縮む）
  - LZSA2 は「長さごとにいちばん近いオフセット」だけを試すと 100.75% で止まった。命令の並びをくらべると、本家は rep-match が約 2,000 回多かった。そこで「長さは伸びないが遠いオフセット」の一致も各位置で 16 個まで試し、arrival を 32 個残すようにして 100.00% になった（後で rep-match になるオフセットを先に選べる）
  - 効かなかったこと: 短い長さをすべて試す範囲（64 → 256）、長い一致の内側を飛ばす長さ（256 → 1024）、arrival をリテラルの数でも分けること
- raw block は、本家と同じく入力も圧縮後も 64KB まで（縮まない 64KB のデータは raw block にできない。`CompressError::TooLarge`）。空の入力の raw block は、本家は 0 バイトのファイルにするので、自作の展開器も 0 バイトを空のデータとして受け付ける
- 本家の仕様書と実装が違った所: 仕様書では raw block の LZSA2 の終わりの印は「9 ビットのオフセット + 長さの EOD」だが、本家の圧縮器は rep-match（トークンの XYZ = 111）+ 長さの EOD を書く。自作も本家の書き方に合わせた（展開器はどちらでも読める）
- 測っていないこと: 486 での展開の速さ（x86 の展開ルーチンは作っていない。組み込みの計画で扱う）

`modern-look`（M1〜M6）で、デスクトップはフルカラー・なめらかな文字・角の丸いウィンドウと影になった。
オーナーが別の場で作ったデザインのモックアップ「Aster」（縁の無いウィンドウ・タイトルバーと中身の一体化・大きく柔らかい影）と比べると、
まだ古く見える所が残っている。仕組み（32 ビットの重ね合わせ・1 行ずつの合成・部品のライブラリ・システムコール）はそのままにし、
色・縁・影・角・バー・背景の描き方を変えて Aster に近づけ、Aster にあるドック（画面の下のアプリのアイコンの並び）を足す。

## 1. 今の状態と困っていること

## 2. ゴール

- ウィンドウ・メニューは縁が無く、2 層の影で背景と分かれる。手前のウィンドウは影が大きく濃い
- タイトルバーは中身と同じ地で線が無い。フォーカスの無いウィンドウは、地はそのままで文字・アイコン・強調色を薄くする
- 角はウィンドウ・メニューが 14、小さな部品が 6
- タイトルバーのボタンは丸い薄い地の付いたアイコン（乗せると濃く、閉じるは赤に白）
- 部品は枠の無い塗りのボタン・欄・一覧。フォーカスの輪はそのまま
- 上端のバーは地を塗らず、背景の上に白い文字とアイコン
- 既定の背景は紫の地に大きな円（ファイルは要らない。起動時の計算だけ）
- 端末のウィンドウはタイトルバーも暗い色
- 画面の下にドックを出す。既定の中身はアイコンのある GUI のアプリ。押すと起動し、起動しているアプリはウィンドウを前に出す
- README のスクリーンショットのシナリオを見直し、ウィンドウの間に余白を取る
- レトロモード（320x200）の見た目は変えない

**やらないこと**:
- タイトルバーの高さ（24）・バーの高さ（24）・ボタンの押せる所の位置の変更。変えるとシナリオのマウスの座標がほぼ全部ずれる（§7）
- アプリの部品の並び（`files` のサイドバーなど、モックアップの配置そのもの）。色と描き方だけ変える
- 通知・デスクトップのアイコン（モックアップにはあるが、別の機能になる）
- ドックの並べ替え（ドラッグ）・マウスでドックに足す/外す操作・ドックを隠す動き。中身を変えるのは `DOCK.CFG` を書き換えて行う
- ぼかし（すりガラス）・半透明のウィンドウ・アニメーション（modern-look と同じく 486 では重い）
- アプリごとに暗いタイトルバーを選べるようにすること（端末だけ。カーネルが持つウィンドウなので）

## 3. 設計の要点

### 3.1 テーマ（`crates/vibe-gfx/src/theme.rs`）

色と大きさはすべてここで変える（カーネルの `gui` とアプリの `vibe-ui` が同じものを使う仕組みはそのまま）。
目標の値（Aster のモックアップの値。§6 の 1・5 の答えで確定）:

| 名前 | 今 | 変えた後 | 使う所 |
|---|---|---|---|
| `FACE` | 250, 250, 251 | 255, 255, 255 | ウィンドウ・メニューの地。フォーカスの有無で変えない |
| `FACE_INACTIVE` | 232, 233, 237 | （無くす） | |
| `SUBTLE`（新） | — | 241, 239, 232 | タイトルバーのボタンの地・部品の塗り・一覧の地 |
| `HOVER` | 222, 224, 230 | 211, 209, 199 | 乗せたボタンの地 |
| `TEXT` / `TEXT_DIM` | 32, 33, 36 / 128, 131, 138 | 44, 44, 42 / 136, 135, 128 | 文字 / 薄い文字 |
| `ACCENT` / `ACCENT_LIGHT` | 青 37, 99, 235 / 219, 230, 252 | 紫 83, 74, 183 / 206, 203, 246 | 強調色（§6 の 1）。選んだ行・メニューの項目の地は `ACCENT_LIGHT` |
| `ACCENT_TEXT`（新） | — | 38, 33, 92 | 薄い強調色の地の上の文字（§6 の 2） |
| `BORDER` | 176, 179, 186 | （ウィンドウ・メニューでは使わない） | |

`deco::panel_row` の角の下の色を取っておく配列は `2 * theme::RADIUS` なので、半径を変えても大きさは自動で合う（カーネルスタックに 112 バイト）。

### 3.2 ウィンドウとメニューの縁（`kernel/src/gui/deco.rs`）

- `panel_row` の `border` を `Option<u32>` にし、`None` なら縁を描かない。角は「中身」と「下の色」を外側の覆う割合だけで混ぜる（今の内側の角の計算が要らなくなるので、少し軽くなる）
- 描く矩形は縁の分を広げず、タイトルバーと中身そのもの（`w.x`, `w.y - TITLE_H`, `w.w`, `w.h + TITLE_H`）にする。広げたまま地の色で塗ると、中身の地が白でないアプリ（`mines` など）の横に白い線が出るため。当たり判定と描き直す行の計算は今の 1 ピクセル広い矩形のまま残す（つかめる所・押せる所を変えない）
- 下の角は半径 14 で中身の角を少し削る（今も半径 8 で削っている。アプリの描く物が角の近くにあると欠ける）
- メニューのパネルも同じ（`draw_menu_row`）

### 3.3 影を 2 層に（`vibe-gfx` の `Shadow`・`deco`）

- 近い影（ぼかし 3・下へ 1）と遠い影（ぼかし 20・下へ 10）の 2 つの表を作り、遠い影 → 近い影の順に重ねる。濃さ（255 が真っ黒）:

  | | 近い影 | 遠い影 |
  |---|---|---|
  | フォーカスのあるウィンドウ・メニュー | 64 | 128 |
  | フォーカスの無いウィンドウ | 50 | 72（下へ 6） |

  影の色は黒ではなく背景の暗い色（4, 0, 30）にする（紫の地になじむ）
- `SHADOW_MARGIN`（描き直す行の広がり）は遠い影の「ぼかし + 下へ」で 30 になる（今は 16）。ウィンドウを動かしたときに描き直す行が少し増える
- **速さ**: 今の `shadow_round` は、影の範囲の行ではウィンドウの中身の幅もピクセルごとに調べて飛ばしている。2 層にすると倍になるので、中身の下（角の外でない所）は列をまとめて飛ばすようにする。ktest の `gfx_compose_speed` を 2 層の影・縁なし・半径 14 に合わせ、変える前と後の時間を LOG.md に残す（上限の 100ms はそのまま）

### 3.4 タイトルバー（`kernel/src/gui/mod.rs` の `render_titlebar`）

- 地はいつも `FACE`。下の区切りの線を描かない
- フォーカスが無ければ題名を `TEXT_DIM`、アイコンを薄く（アルファを半分にして描く。`blit_alpha` に濃さの引数を足すか、薄くした写しをウィンドウを作るときに作っておく）
- ボタンは押せる所（幅 `BUTTON_W` = 20、位置はそのまま）の真ん中に直径 20 の丸（`Corner` の半径 10）をいつも `SUBTLE` で描き、乗せたら `HOVER`（閉じるは `CLOSE_HOVER` に白い記号）。記号は今の線の記号を少し小さく（8x8）
- **端末**: カーネルが作る端末のウィンドウは、タイトルバーの地を端末の地の色（`theme::TERMINAL[0]`）、題名を明るい灰色にする（`Window` に「暗いタイトルバー」の印を持たせる）。ボタンの丸は暗い地に合う色（68, 68, 65 / 乗せると 95, 94, 90）
- タイトルバーと中身の境目は線が無いので、`client_row` の 1 行目まで同じ地が続く。中身の地が `FACE` と違うアプリ（8 ビットの `mines` など）はそのまま境目が見えるが、それでよい

### 3.5 上端のバー（`kernel/src/gui/bar.rs`）

- バーの地を塗らず、`render_bar` で背景（§3.6 の地と円、または背景の画像）の行を先に `self.bar` に描いてから文字を重ねる。背景の画像を変えたとき（`wallpaper_set`）と画面の大きさを決めたときに `bar_dirty` にする
- 区切りの線を描かない。文字（「VibeOS」・ウィンドウの題名・状態の表示）は `BAR_TEXT`。最小化したウィンドウは薄く
- フォーカスのあるウィンドウのボタン・開いているメニューのボタンは、白を 20% 重ねた角の丸い地（今の `ACCENT_LIGHT` の代わり）
- 背景の画像を使っているときは、明るい画像でも白い文字が読めるよう、バーの範囲に黒を 35% 重ねる（§6 の 3）。既定の背景では重ねない
- メニュー（開いたパネル）は今のまま明るい地（縁なし・2 層の影）。乗せた項目は薄い強調色の地に濃い強調色の文字（§6 の 2）

### 3.6 背景（`compose_desktop_row`・`vibe-gfx`）

- 既定の背景は、地の色 1 色に、画面の大きさに対する割合で置いた大きな円をいくつか重ねたもの（Ver.5 のモックアップ: 右上に半径が画面の高さの 2/3 ほどの 83, 74, 183、左下に半径 3/8 ほどの 38, 33, 92）
- 円は 1 行ずつ「その行で円が占める x の範囲」を整数の平方根で求めて塗る（画面の大きさの画素を作らない。今の 1 行ずつの重ね合わせのまま）。範囲の両端の 1 ピクセルは、はみ出す割合で混ぜて縁をなめらかにする（1/16 ピクセル単位で計算）
- 円の並びと色は `theme` の表に置き、計算は `vibe-gfx` の関数（`fill_row` と同じ形）にしてホストでテストする
- 背景の画像（`wallpaper=`）があるときは今までどおりそれを並べる。真ん中に置いたときの周りは、グラデーションの代わりにこの背景

### 3.7 部品（`crates/vibe-ui`）

- ボタン: 枠を描かず `SUBTLE` で塗る。乗せたら `HOVER`、押したらもう一段濃く。既定のボタン（`default`）は強調色の地に白い文字
- テキスト欄・一覧・表示欄: 枠を描かず `SUBTLE` で塗る（ウィンドウの地の白と分かれる）。フォーカスの輪（強調色の 2 ピクセル）は今のまま
- 一覧の選んだ行: 薄い強調色の地に濃い強調色の文字（§6 の 2）。フォーカスの無いウィンドウでは灰色（`HOVER`）
- スクロールバーのつまみは細く（幅 6 の丸）
- 色は `draw.rs` の定数を `theme` の値に置き換えるだけで、部品の配置（`Rect`）は変えない。ホストのテスト（配置・入力・状態）はそのまま通るはず
- 各アプリ（`calc`・`files`・`tasks`・`clock`・`mines`・`blocks`）は描き直しのコードを変えずに新しい色になる。アプリが自分で使っている色（`blocks` の盤の地など）は、浮いて見える所だけ直す

### 3.8 ドック（`kernel/src/gui/dock.rs`（新）と、ホストでテストする部分は `vibe-gfx` の `dock`（新））

- 画面の下の真ん中に浮かぶ、角の丸い暗いパネル（地 38, 33, 92、半径 20、2 層の影）。下端から 12 離す。上端のバー・メニュー・カーソルと同じくカーネルの `gui` が描き、ウィンドウより手前・メニューとカーソルより奥に重ねる。レトロモード（320x200）では出さない
- **項目**: `/SYSTEM/DOCK.CFG`（1 行に 1 つのアプリの名前。`#` より後ろはコメント。`terminal` は端末）に書いた順に並べる。起動時に読む。ファイルが無いか中身が空ならドックを出さない
- **既定の中身**: アイコンが定義されているアプリ（`assets/icons/` に同じ名前の SVG があるもの）のうち、引数なしでウィンドウを開く GUI のアプリ。今は次の 11 個:

  `terminal files calc clock tasks mines blocks paint life snake mandel`

  ファイルの種類のアイコン（`app`・`file`・`folder`・`image`・`script`）と、端末で動くか引数の要るアプリ（`edit`・`view`）は入れない。GUI のアプリかどうかは ELF からは分からないので、Makefile に `DOCK_APPS` として並べ、ビルドで `DOCK.CFG` を作る。`DOCK_APPS` の名前に SVG が無ければビルドを止める（アイコンが定義されていることを守る）。新しい GUI のアプリにアイコンを足したら `DOCK_APPS` にも足す
- `/BIN` に無いアプリ（圧縮しないイメージには `RAW_APPS` しか入らない）は出さない。アイコンの無い名前を書いたら汎用のアイコン（`app`）
- **1 つの項目**: 40x40 の角の丸いタイル（半径 12、地は `ACCENT_LIGHT`）の真ん中に 32x32 のアイコン（§6 の 7。無ければ 16x16）。タイルの間は 8。乗せるとタイルを明るくし（`FACE`）、タイルの上にアプリの名前の小さなパネル（ツールチップ。明るい地・縁なし・影）を出す
- **開いているアプリ**: そのアプリのウィンドウ（最小化したものも）があれば、タイルの下に直径 4 の点
- **押したとき**: そのアプリのウィンドウがあれば一番手前のものを前に出す（最小化していれば戻す）。無ければ起動する（メニューの `launch` と同じ。§6 の 8）。端末は、端末のウィンドウがあれば前に出す（新しい端末はメニューの "Terminal" か Alt+F1〜F4）
- どのウィンドウがどのアプリかは、ウィンドウを作ったプロセスのプログラムの名前（今 `add_window` でアイコンを選ぶのに使っている `app`）を `Window` に持たせて決める。カーネルの端末は `terminal`
- **作業領域**: ドックに隠れないよう、新しいウィンドウを置く位置と端末の大きさの上限は、画面の下からドックの分（タイル 40 + 上下の余白 7×2 + 下端から 12 = 66）を除いた範囲で決める。ウィンドウをドラッグしてドックの裏に入れるのは自由（Aster・macOS と同じ）
- 項目が画面の幅に入りきらなければ、入る分だけ出す（640x480 でも 11 個は入る: 11 × 48 + 余白 ≒ 544）
- **描き方**: メニューと同じく、パネルの中身を 1 枚のバッファ（11 個で約 548 × 54 × 4 ≒ 118KB）に描いておき、重ね合わせで `panel_row` で 1 行ずつ重ねる。ツールチップも同じ。描き直すのは、乗せた項目・開いているアプリが変わったときだけ
- **ホストのテスト**: `DOCK.CFG` の読み方、項目の数と画面の幅からの配置、座標から項目を引く当たり判定、作業領域の計算は `vibe-gfx` の `dock` に置く（カーネルの `gui` はそれを使う）

## 5. ブランチの進め方

- ブランチ `aster-look`（main の `85188d2` から）。main に合流するかは、A1 か A4 の後にスクリーンショットを見てオーナーが決める
- コミットは D-039 のとおり、計画書を順番に実行している間は段階ごとにコミットする。スクリーンショットの変更だけは外し、オーナーの確認の後で別にコミットする（D-055）。push はしない
- 文書（PLAN.md・LOG.md・DECISIONS.md・DESIGN.md）もこのブランチの上で更新する。D-047 の「1 ピクセルの薄い縁」「強調色の青」はこのブランチでは覆すことになるので、着手するときに DECISIONS.md に残す
- main で `gui`・`vibe-ui`・`vibe-gfx` を変えると合流のときにぶつかる。main で作業が進んだら、段階を始める前に取り込むかをオーナーに確認する
- 合流しないと決めた場合も、ブランチは消さずに残す

2. **選んだもの（一覧の行・メニューの項目）の見せ方**: Aster と同じ「薄い強調色の地（206, 203, 246）に濃い強調色の文字（38, 33, 92）」にする。フォーカスの無いウィンドウでは灰色の地
3. **背景の画像の上のバー**: 背景の画像があるときだけ、バーの範囲に黒を 35% 重ねる。既定の背景では重ねない
4. **タイトルバーの高さ**: 今の 24 のまま。Aster に合わせて高くするのは、やるなら別の段階（A5）にする
5. **既定の背景**: Aster と同じ「紫の地に大きな円」にする（§3.6）
6. **main への合流**: 未定にして、A1 の後のスクリーンショットを見てオーナーが決める

ドック（D-058 で足した）について、D-059 で答えをもらった（すべて推奨のまま）:

7. **ドックのアイコンの大きさ**: ドック用に 32x32 のアイコンを同じ SVG から作る（`vibe-icongen` で大きさを選べるようにし、ドックのアプリの分だけ `/SYSTEM/ICONS32.VIA` に入れる。gzip で 10KB 前後の見込み）。今のアイコンは 16x16 だけ（D-051）で 40x40 のタイルには小さく、2 倍に引き伸ばすと角ばるため。圧縮しないイメージに入らなければ、そちらは 16x16 のまま（真ん中に小さく出す）
8. **起動しているアプリを押したとき**: ウィンドウを前に出す（無ければ起動）。「いつも新しく起動する」は、電卓などのウィンドウが増えていくのでやめた。新しい端末はメニューの "Terminal" か Alt+F1〜F4 で開く
9. **上端のバーのウィンドウのボタン**: 残す。ドックはアプリ単位、バーはウィンドウ単位で役目が違い、ドックの点だけでは同じアプリの 2 つ目のウィンドウ（端末の 2 つ目など）を選べないため

## 7. 心配な点

- **速さ**: 影を大きく・2 層にすると、ウィンドウの周りで合成するピクセルが今の 3 倍ほどになる。中身の下を飛ばす工夫（§3.3）で抑えるが、486 の実機ではウィンドウを動かすときに遅くなるおそれがある（モダンを実機で使えるのは VESA 2.0 の 32 ビットのカードのある機械だけなので、影響は小さい見込み）
- **影が見えない**: 縁を無くすと、ウィンドウどうしが重なった所は影だけが頼りになる。白いウィンドウが白いウィンドウの上に重なると境目が薄い。遠い影を十分濃く（§3.3 の 128）し、スクリーンショットで確かめる。足りなければ、フォーカスの無いウィンドウだけごく薄い縁（地より 4% 暗い）を残すことを検討する
- **8 ビットのアプリ**: `mines`・`blocks`・`paint`・`snake` などの 8 ビットのウィンドウは、中身の地が白でないとタイトルバーとの境目が見える。今と同じなので悪くはならないが、Aster ほど一体には見えない
- **期待画像の作り直し**: 画面を比べるシナリオのうち、デスクトップのもの（12 本、38 枚の期待画像の半分以上）がほぼ全部変わる。段階ごとに 1 枚ずつ目で確かめる手間が大きい
- **当たり判定**: 当たり判定は今の 1 ピクセル広い矩形のままにするので、つかめる所・押せる所は今と同じ。描かれない外側の 1 ピクセル（背景が見える所）を押してもウィンドウに当たる
- **シナリオのクリック**: ドックはウィンドウより手前なので、今のシナリオで画面の下の真ん中（1024x768 で y が約 700 より下、x が約 240〜780）を押しているものはドックを押すことになる。A4 で全部のシナリオのマウスの位置を確かめ、当たるものは押す位置を直す
- **640x480 の端末**: 作業領域がドックの分（66）狭くなるので、640x480 の画面では端末の行が減る（`25-video-640` の期待画像が変わる）
- **圧縮しないイメージの空き**: `DOCK.CFG` は小さいが、32x32 のアイコン（§6 の 7）は入らないかもしれない。入らなければ `COMPRESS=0` のときだけ入れない
- **角で欠ける中身**: 半径を 14 にすると、中身の下の角が今より大きく欠ける。アプリの部品（`tasks` の下のボタンなど）が角に近いと欠けるので、A2 で余白を確かめる

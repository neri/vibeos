# 計画書: タイトルバー・メニュー・ドックをすりガラスにする（後ろをガウスぼかしで透かす）

状態: **G2 完了**（§6 はオーナーが答えた: DECISIONS.md D-071。オーナーが「計画書どおり G1 から実装をはじめて」、G1 のスクリーンショットを見て「この見た目で G2（メニュー・ドック）に進んで」） / ブランチ `test/blur`（main の `8f834c9` から）で作業する / 作成: 2026-10-23 / 作成者: AI

aster-look（A1〜A4）で、ウィンドウは縁が無く、タイトルバーは中身と同じ白い地になった。
この計画では、タイトルバーを **すりガラス** にする: タイトルバーの後ろにある物（背景・奥のウィンドウとその影）を
ガウスぼかし（ガウシアンブラー）でぼかし、その上に白（端末は暗い色）を薄く重ねて、題名とボタンを描く。
奥の物の色がにじんで透けて見えるので、ウィンドウが背景の上に浮いた 1 枚の板に見える（macOS・Windows 11 のタイトルバーと同じ考え方）。
同じ仕組みで、メニュー（開いたパネル）とドックのパネルもすりガラスにする（§6 の 5）。

modern-look（§2 のやらないこと）と aster-look（§2 のやらないこと）では「ぼかし（すりガラス）は 486 では重い」として外していた。
この計画は、それを **タイトルバー・メニュー・ドックだけ・変わったときだけ計算する** 形に絞ってやる（前の判断を覆すことは D-071 に残した）。

## 1. 今の状態

| 今 | 困ること・変える理由 |
|---|---|
| タイトルバーは `render_titlebar` が白（端末は暗い色）で塗りつぶした 32 ビットのバッファ（`Window::titlebar`）。フォーカス・乗せたボタン・題名が変わったときだけ描き直す。メニュー（`render_menu`）とドック（`render_dock`）も、塗りつぶした自分のバッファに描いておき、重ね合わせで写す | 後ろの物は何も透けない。ウィンドウの重なりは影だけで見せている |
| 重ね合わせは 1 行ずつ（`present` → `compose_desktop_row`）。1 行を背景 → 奥のウィンドウから順に（影・中身・角）→ ドック → メニューと重ね、すぐに VRAM へ送る | ぼかしは上下の行の色も要るので、1 行ずつの合成の中ではできない。別の所で先に計算しておく必要がある |
| 描き直す範囲は行の範囲（`dirty_lo`〜`dirty_hi`）だけで、どのウィンドウのどこが変わったかは持っていない | ぼかしをいつ計算し直すかを決められない（行だけで決めると、端末が 1 文字出すたびに上の全部のタイトルバーを計算し直す） |
| カーネルでは FPU を使わない。影の表（`Shadow`）・角（`Corner`）も整数だけで作っている | ガウス関数（exp）を実行時に浮動小数点で計算できない |

## 2. ゴール

- デスクトップ（32 ビットの画面）で、すべてのウィンドウのタイトルバー（§6 の 4）・メニュー・ドックのパネルがすりガラスになる。後ろの背景の円・奥のウィンドウ・その影がぼけて透ける
- ぼかしは整数だけで計算し、ガウス関数のぼかしとほぼ同じ見た目にする（§3.1。ホストのテストで本物のガウスぼかしと比べる）
- 奥の物が動いた・描き変わったときは、そこに重なるタイトルバー・パネルだけを計算し直す。重ならない所の変化では計算しない
- 題名・アイコン・ボタン・メニューの項目・ドックのタイルは今と同じ位置・大きさ。タイトルバーのボタンの丸は半透明にしてガラスが透けるようにする
- `BOOT.CFG` の `blur=off` で今の見た目（不透明のタイトルバー・メニュー・ドック）に戻せる。遅い機械のため
- README のスクリーンショットを撮り直す（D-055。オーナーが確かめるまでコミットしない）

**やらないこと**:
- 上端のバー（もともと地を塗らず背景の上に描いている）・ドックのツールチップ（小さく、文字だけなので不透明のまま）・ウィンドウの中身のすりガラス
- ウィンドウ全体の半透明、アニメーション
- タイトルバーの高さ（24）・ボタンの位置・当たり判定の変更（シナリオのマウスの座標がずれるため）
- レトロモード（8 ビットの画面・320x200）。デスクトップの飾りが無いので今のまま
- アプリから「このウィンドウはすりガラスにしない」と選べるようにすること

## 3. 設計の要点

### 3.1 ぼかしの計算（`crates/vibe-gfx/src/blur.rs`（新）。ホストでテストする）

- **3 回の箱ぼかしでガウスぼかしを近似する**（§6 の 1）。幅 `2k + 1` の箱（範囲の平均）を横・縦それぞれ 3 回かけると、
  重みは 2 次のスプラインになり、標準偏差 σ² = 3 × ((2k + 1)² − 1) / 12 のガウス関数にほぼ一致する（中心極限定理。よく使われる近似）
  - 箱ぼかしは「足し込んだ合計に 1 つ足して 1 つ引く」だけなので、1 ピクセルの計算の量がぼかしの大きさによらない。本物のガウス関数の重みを掛けると、σ に比例して掛け算が増える（σ = 6.5 で 1 ピクセル 1 方向あたり 39 回）
  - `k = 6`（幅 13）で **σ ≈ 6.5**（§6 の 2）。ぼかしが届く幅は片側 `3k` = 18 ピクセル
  - 平均は割り算をせず、表（合計 → 丸めた平均。32KB）を引いて求める（486 の DIV は遅い。G1 では初め逆数を掛けていたが、表の方が速かった）。真っ白・真っ黒の一様な画像がそのまま残ることをテストで確かめる
  - 縦 → 横の順にかけ、タイトルバーの行と列だけを計算する（`Blur::apply_region`。縦の 2 回目・3 回目は次の回が読む行だけ、横はタイトルバーの行だけ）。画像全体をぼかしたときと同じ結果になることをテストで確かめる
  - 色は R・G・B を別々の `u32` の合計で数える（幅 13 × 255 でも溢れない）。アルファは扱わない（ぼかすのは不透明な重ね合わせの結果だけ）
- 画像の外は **端のピクセルを伸ばす**（clamp）。画面の端にあるタイトルバーが端だけ暗く・明るくならないように
- API: `Blur::new(k)`（表を作る）と `Blur::apply`・`apply_region(img, w, h, tmp, 矩形)`。`tmp` は呼ぶ側が用意する（カーネルではスタックに大きな値を置かない）。縦の箱は 1 列ずつ `tmp` に写してから横と同じ処理を通す
- テスト専用に、f64 で計算した本物のガウスぼかし（同じ σ、±4σ で打ち切り、端は clamp）を `#[cfg(test)]` の中に置いて比べる。ホストのテストなので浮動小数点を使ってよい（カーネルに入るコードは整数だけ）

### 3.2 すりガラスの色（`theme`）

- ぼかした後ろの色に重ねる色と濃さ（§6 の 3。端末とドックの値は AI が決めた仮の値で、G1・G2 の後のスクリーンショットで調整する）:

  | 所 | 重ねる色 | 濃さ |
  |---|---|---|
  | タイトルバー・メニュー | `FACE`（白） | 50%（128） |
  | 端末のタイトルバー | `TERMINAL[0]`（暗い色） | 80%（204） |
  | ドックのパネル | `DOCK`（濃い紫） | 70%（179） |

  - 例: 白 50% は、背景の明るい紫の円（83, 74, 183）の上で約 (169, 165, 219)、濃い紫の地（60, 52, 137）の上で約 (158, 154, 196)
  - 文字の読みやすさ: 既定の背景の上なら、題名（44, 44, 42）とのコントラスト比は 5 前後。ただし後ろが真っ黒（端末の地など）だと白 50% は (128, 128, 128) になり、比は約 3.6 で 4.5 に届かない（§7）。端末は真っ白の上でも (72, 73, 78) で、文字（222, 221, 214）と 4.5 以上
- フォーカスの有無で重ねる色は変えない（今と同じく、題名・記号・アイコンを薄くするだけ）
- タイトルバーのボタンの丸は不透明の `SUBTLE`・`HOVER` をやめ、黒を 7%・17% 重ねる（暗いタイトルバーは白を 10%・18%）。閉じるに乗せたときの赤（`CLOSE_HOVER`）は今のまま不透明
- メニューの乗せた項目の地（`ACCENT_LIGHT`）、ドックのタイル（`ACCENT_LIGHT`・乗せると `FACE`）と開いているアプリの点は今のまま不透明
- 値は `theme` の定数にする（`GLASS_BLUR_K`・`GLASS_TINT_ALPHA`・`GLASS_DARK_TINT_ALPHA`・`GLASS_DOCK_TINT_ALPHA`・ボタンの濃さ）

### 3.3 どこで計算するか（`kernel/src/gui/glass.rs`（新））

1 行ずつの合成はそのままにし、**行を合成する前に**、ガラスを計算し直す必要のある物を奥から順に処理する（`present` の最初）。
すりガラスの物（以下「ガラス」）は、奥から **ウィンドウのタイトルバー（重なりの順）→ ドックのパネル → メニュー** の順に並ぶ。

1. **後ろの画像を作る**: ガラスの矩形（タイトルバーなら `w.x`, `w.y − TITLE_H`, `w.w`, `TITLE_H`）を上下左右に `3k` 広げた範囲を、画面の中に切り詰めて、
   「背景 → そのガラスより奥の物」だけで 1 行ずつ合成する（`compose_desktop_row` の、途中で止める版）。
   - タイトルバー: 背景 → そのウィンドウより奥のウィンドウ（影・タイトルバー・中身・角）。そのウィンドウ自身の影は入れない
   - ドック: 背景 → すべてのウィンドウ
   - メニュー: 背景 → すべてのウィンドウ → ドック（ツールチップは入れない）
   - ガラスより手前の物とカーソルは入れない（後ろにある物ではないため）。上端のバー（y < `BAR_H`）の行は背景だけ（バーはウィンドウより手前で、地は透明なので、その後ろは背景）
2. **ぼかす**（§3.1）。範囲の外は clamp
3. **色を重ねて**（§3.2）ガラスの大きさに切り出し、取っておく（タイトルバーは `Window::glass`、メニュー・ドックはそれぞれの構造体）
4. **描き直す**: `render_titlebar`・`render_menu`・`render_dock` は `c.clear(色)` の代わりに取っておいたガラスを写してから、今までどおり中身を描く（文字は下の色と混ぜて描くので、ガラスの上でもなめらかになる）。
   乗せたボタン・項目、フォーカス・題名が変わっただけのときは、ぼかしを計算し直さずガラスから描き直す
5. その行を描き直す行に入れる

- 奥のタイトルバーもすりガラスなので、奥から順に処理すれば、手前の物は計算し直した奥のガラスを透かして見る
- `blur=off` のときはガラスを作らず、今と同じく塗りつぶす（今の見た目とピクセルまで同じ）
- **バッファ**: 後ろの画像用に 1 つ（タイトルバーは「画面の幅 ×（`TITLE_H` + 6k）」で 1024 で 1024 × 60 × 4 ≒ 240KB。メニューはそれより大きいことがあるので、いちばん大きい物に合わせて確保し直す）と、縦の箱用の 1 列分。ガラスはタイトルバーごとに幅 × 24 × 4（幅 1024 で 96KB）、メニュー・ドックはパネルの大きさ分。どれもヒープ（`Box`/`Vec`）に置き、スタックには置かない

### 3.4 いつ計算し直すか（変わった所の一覧）

行の範囲だけでは足りないので、1 回の `present` までに **変わった矩形と、それがどの深さ（§3.3 の並びの何番目）の物か** を短い一覧に貯める。

| 起きたこと | 一覧に足すもの |
|---|---|
| ウィンドウの中身が描き変わった（`mark_window_dirty`） | 中身の矩形のうち変わった行の範囲、深さはそのウィンドウ |
| ウィンドウを動かした | 前と後の矩形（影の分 `SHADOW_MARGIN` を含む）、深さはそのウィンドウ |
| 前に出した・最小化・戻した・作った・閉じた（重なりの順が変わる）、フォーカスが変わった（影の濃さが変わる） | 全部（G1 で簡単にした。どれも `focus_changed` を通り、画面全体も描き直している。クリックのときだけなので、全部を計算し直しても目立たない） |
| 独自のパレットを変えた | 全部 |
| 背景の画像を変えた・デスクトップにした | 画面全体、深さは一番奥 |
| タイトルバー・ドックを描き直した（ガラス・乗せたボタンや項目・題名・開いているアプリの点） | その矩形（影を含む）、深さはそのガラス |
| メニューを開いた | メニューのガラスを必ず計算する（開いている間だけ持つ） |

- ガラス G は、一覧の中に「G より奥」かつ「G の矩形を `3k` 広げた矩形と重なる」ものがあるときだけ計算し直す
- 一覧は固定長（例えば 16 件）。溢れたら「画面全体・一番奥」の 1 件にまとめる（全部を計算し直す。正しさは保ち、遅くなるだけ）
- 変わった所の一覧は割り込みの中では触らない（今の `mark_rows` と同じく SCREEN のロックの中だけ）

### 3.5 設定

- `BOOT.CFG` の `blur=on|off`。タイトルバー・メニュー・ドックをまとめて切り替える。既定は G1・G2 では `off`、G3 で `on`（§4・§6 の 6）。知らない値は `on` 扱いにして klog に出す
- 起動時に `gui: blur on (k=6)`・`gui: blur off` をシリアルに出す（シナリオで待てるように）

### 3.6 速さの見込み

- 幅 1024 のタイトルバー 1 本: 後ろの 60 行の合成（今の 1 画面 768 行が QEMU で約 10ms なので約 0.8ms）+ ぼかし（約 6 万ピクセル × 6 回 × 3 色の足し引き）+ 色の重ね。QEMU で数 ms、ktest の上限は 10ms にする（測った値を LOG.md に残す）
- ドック（11 個で約 548 × 54）は幅 1024 のタイトルバーより小さい。メニューは項目の数で大きさが変わり、開いたときと、開いている間に後ろが変わったときに計算する
- ウィンドウをドラッグしている間は、そのウィンドウと、その上で重なるガラス（ドックの後ろを通るならドックも）をマウスが動くたびに計算し直す
- 奥で時計・`life`・端末が動き続けると、そこに重なるガラスは描き直しのたびに計算し直す。重ならなければ計算しない
- 486 の実機では幅 1024 の 1 本で数十〜100ms ほどかかる見込み。モダンの見た目を使えるのは 32 ビットの VESA のカードのある機械だけだが、遅ければ `blur=off` で切る（§7）

## 6. オーナーに決めてほしいこと

D-071 で答えをもらった（3 と 5 は推奨と違う方を選んだ）:

1. **ぼかしの計算の仕方**: 3 回の箱ぼかしでガウスぼかしを近似する（推奨のまま）。本物のガウス関数の重みは使わない
2. **ぼかしの強さ**: σ ≈ 6.5（幅 13 の箱。推奨のまま）
3. **重ねる色の濃さ**: 白 50%（**推奨の 70% より透かす**）。端末の暗いタイトルバーは 80%、ドックは濃い紫を 70%（この 2 つは AI が決めた仮の値）
4. **どのウィンドウ**: すべてのウィンドウ（推奨のまま）
5. **範囲**: タイトルバーに加えて **メニュー・ドックにも広げる**（推奨はタイトルバーだけだった。段階 G2 を足した）
6. **既定**: 最後の段階（G3）で `on` にする（推奨のまま）
7. **ブランチ**: `test/blur` で作業し、合流は G3 の後に決める（推奨のまま）

## 7. 心配な点

- **文字の読みやすさ（白 50%）**: 後ろが暗い所（端末・暗い背景の画像・8 ビットのアプリの黒い地）では、タイトルバーとメニューの地が灰色になり、文字とのコントラスト比が 4.5 を下回る（真っ黒の上で約 3.6）。メニューは文字が多いので特に効く。G1・G2 の後のスクリーンショットで、端末の上に重ねたウィンドウ・メニューも撮って見てもらう。読みにくければ、(a) 濃さを上げる、(b) 後ろが暗いときだけ濃くする（ぼかした後ろの明るさの平均で決める）を検討する
- **Aster の「タイトルバーと中身の一体化」が崩れる**: タイトルバーが薄い紫などに色付き、中身の白と境目が見えるようになる（aster-look で消した区切りが、色の違いで戻る）。白 50% なので差ははっきり出る。気になるかは G1 の後のスクリーンショットで見てもらう
- **速さ**: §3.6 のとおり、ドラッグ中と、奥で動き続けるアプリの上では毎回計算する。486 の実機では重い。目安を超えたら、(a) 後ろの画像を縦横 1/2 に縮めてからぼかして戻す（計算は約 1/4、見た目はほぼ同じ）、(b) 計算し直しを一定の間隔（例えば 50ms）に間引く、の順で検討する。どちらもやるなら DECISIONS.md に残す
- **計算し直しの漏れ**: §3.4 の一覧に足し忘れると、奥が変わってもガラスが古いまま残る。シナリオ `74-title-blur`・`75-panel-blur` で主な場合（動かす・描き変わる・前に出す・最小化・閉じる・背景の画像を変える）を画面の比較で確かめる。迷ったら「画面全体・一番奥」を足す（遅くなるだけで正しい）
- **期待画像の作り直し**: タイトルバー・メニュー・ドックが写るデスクトップの期待画像はほぼすべて変わる（aster-look の A1 より多い）。G3 で 1 枚ずつ目で確かめる手間が大きい。ぼかしは整数だけで計算するので、作り直した後は毎回同じピクセルになり、テストが揺れることは無い
- **メモリ**: ウィンドウごとに 96KB（幅 1024）まで増える。ウィンドウが 10 個で約 1MB。モダンの見た目は 640x480 でも 8MB の機械で動いている（`20`）ので、そのシナリオでも確かめる
- **8 ビットのウィンドウ**: 奥の 8 ビットのアプリ（`mines` など）も重ね合わせの結果をぼかすので、特別な扱いは要らない
- **画面の端**: ガラスが画面の端に近いと、ぼかしの範囲の外は端のピクセルを伸ばした色になる。端だけ色が偏ることがあるが、見て分かるほどではない見込み

# 計画書: パイプとリダイレクト

状態: **完了**（Phase 38〜40。§6 の回答は DECISIONS.md D-041・D-042） / 作成: 2026-10-12 / 作成者: AI

シェルで `ls | more`、`cat A.TXT | grep foo > B.TXT` のように、プログラムの出力を別のプログラムやファイルにつなげるようにする。
続く計画（[user-shell.md](user-shell.md)、シェルをユーザ空間へ）の土台にもなる。

## 1. 今の状態と困っていること

| 今 | 困ること |
|---|---|
| ファイル記述子 0〜2 は `syscall.rs` で端末に決め打ち。3 以降は「VFS の番号 + 3」 | 標準入出力をファイルや別のプロセスにつなぎ替えられない |
| 子プロセスは開いているファイルを受け継がない（`TaskFs::new_child`） | 親が用意した入出力を子に渡せない |
| `spawn` の引数は 1 本の文字列で、カーネルが空白で区切り直す | `"a b"` のように空白を含む引数が子に届かない（シェルで `"..."` と書いても分かれる） |
| 内蔵コマンド（`ls`・`cat`・`echo` など 36 個）はシェルのカーネルスレッドの中で `kprint!` で端末に直接書く | 出力をパイプやファイルへ向けられない。パイプの両側が内蔵コマンドだと、同じスレッドの中で書く側と読む側が待ち合って止まる |
| fd 0 の `read` は、端末で 1 行を編集付きで読むだけ | 「入力がパイプかファイルなら中身を読む」というプログラム（`more`・`grep` など）が書けない |
| 端末の「前面のプロセス」は 1 つだけ | パイプでつないだ全部のプロセスを Ctrl+C で止められない |

## 2. ゴール

- シェルで `|`、`<`、`>`、`>>` が使える。`2>` で標準エラーだけ、`2>&1` で標準エラーも同じ先へ向けられる
- パイプでつないだプロセスは同時に動き、書く側が終わると読む側に終わり（EOF）が届く
- 空白を含む引数が、そのまま子プロセスに届く。環境変数を子プロセスに渡せる（シェルから使えるのは次の計画）
- 標準入力から読むフィルタのアプリ（`grep`・`wc`・`head`・`sort` など）があり、`more` も標準入力から読める
- Ctrl+C でパイプの全部のプロセスが止まる
- 今あるシナリオは、そのままか、出力の違いを直すだけで通る

**やらないこと**: シェルの文法（変数・`if`・`for`・`;`・`&&`）とユーザ空間のシェル（次の計画）, シグナルの仕組み, 名前付きパイプ（FIFO）, `fork`, ジョブ制御（`fg`・`bg`・Ctrl+Z）

## 3. 設計の要点

### 3.1 ファイル記述子の表をそろえる（いちばん土台になる変更）

- `TaskFs` の表の番号を、そのままファイル記述子にする（「+ 3」をやめる）。表の 1 件は次のどれか:
  - `Console`（端末。今の fd 0〜2 の動き）
  - `File`（今のファイル）, `Socket`（今のソケット）
  - `PipeRead` / `PipeWrite`（§3.2）
- 1 件を `Arc` で持ち、複数の fd・複数のプロセスで同じものを指せるようにする。ファイルの読み書きの位置も共有する（Unix の「開いたファイルの記述」と同じ。`cmd >> LOG.TXT 2>&1` で同じ位置に書くため）
- 新しいプロセスの 0〜2 は、何も指定しなければ親の 0〜2 を受け継ぐ。3 以降は受け継がない（パイプの書く側が残って EOF が来なくなるのを防ぐ）
- `close` は表から外すだけ。最後の参照が無くなったときにファイルの書き込み・パイプの片側の閉じ・ソケットの閉じが起きる
- `dup2(old, new)` を足す（アプリが自分の入出力をつなぎ替えるため。次の計画のシェルも使う）

### 3.2 パイプ

- カーネルの中のリングバッファ（4KB）。読む側と書く側にそれぞれ `WaitQueue` を置き、空なら読む側が、満杯なら書く側が待つ（DESIGN.md §6.4 の約束どおり）
- 書く側・読む側の数を数える。書く側が 0 で空なら `read` は 0（EOF）を返す
- 読む側が 0 のときの `write`: 書いたプロセスを終了コード -141 で止める（Unix の SIGPIPE と同じ動き。`yes | head` で `yes` が止まる）。`ctrl_c(CATCH)` と同じように、自分で扱いたいプロセス向けに `-EPIPE` を返すようにもできる（§6 の 3）
- Ctrl+C などで止めるよう頼まれたら、パイプを待っているプロセスも起きて `-EINTR` で戻る（今のキーやソケットと同じ）
- `pipe(&mut [fd; 2])` のシステムコールを足す

### 3.3 プロセスの起動に入出力と引数を渡す

- `spawn_ex(path, argv, envp, &[fd; 3])` を足す。`argv` は 0 区切りの並び（空白を含む引数がそのまま届く）、`envp` は `名前=値` の 0 区切りの並び（環境変数。DECISIONS.md D-040）、`[fd; 3]` は子の 0〜2 にする親の fd（-1 なら親の同じ番号）
- `fork` が無いので、`posix_spawn` と同じ「起動するときに入出力と環境を決める」形にする
- 子のスタックには `[argc][argv...][NULL][envp...][NULL]` と文字列を積む（Unix の `_start` と同じ並び）。`argv` と `envp` は合わせて 16KB まで（スタックは 64KB）
- 環境はカーネルが覚えておくものではなく、各プロセスのメモリの中にある。子に何を渡すかは親が決める。`vibe-rt` の `env()`・`var(名前)` で読み、`set_var`・`remove_var` で自分の分を変える
- 今の `spawn` のシステムコールは残す（環境は空で起動する）。`vibe-rt` の `spawn` は `spawn_ex` を使い、今の環境をそのまま渡す（今のアプリは作り直すだけで親の環境を受け継ぐ）。`vibe-rt` に `Command` 風の組み立て（`.arg()`・`.env()`・`.stdin()`・`.stdout()`・`.spawn()`）を足す
- カーネルが起動するプロセス（端末のシェルなど）は空の環境で始まる

### 3.4 標準入力が端末かどうか

- 端末の fd 0 の `read` は今どおり 1 行の編集付き入力。パイプとファイルは中身をそのまま読む
- `fd_kind(fd)`（端末・ファイル・パイプ・ソケット）を足し、`vibe-rt` に `isatty(fd)` を用意する
- キー入力（`getkey`）は今どおり端末から取る。だから `ls | more` で、`more` は文字をパイプから読み、スペースキーを端末から読める
- `more` は、ファイル名が無ければ標準入力を読む。出力が端末でなければ、1 画面ずつ止めずに全部書く

### 3.5 シェル（カーネルの中のまま）

- 1 行を「コマンドの並び + つなぎ方」に分ける部分を `crates/vibe-shell`（新規、`no_std` + `alloc`）に置き、ホストの `cargo test` で確かめる。次の計画のユーザ空間のシェルも、このクレートを使う
  - 文法: `cmd [args] [< file] [> file | >> file] [2> file | 2>&1] { | cmd ... } [&]`。`"..."` と `'...'` で空白・記号を含められる
- 実行: 必要な数のパイプを作り、各コマンドを `spawn_ex` で起動し、シェル側のパイプの fd を閉じてから全部を待つ。終了コードは最後のコマンドのもの
- 前面のプロセスを「プロセスの集まり」にする（`set_terminal_foreground` に複数の番号）。Ctrl+C はその全部に届く
- `&` を付けたパイプは全部を裏で動かす

### 3.6 内蔵コマンドの扱い

よく使う小さなコマンドは内蔵のまま残す（アプリの読み込みと展開を待たずに動き、フロッピーも使わない。DECISIONS.md D-041）。その代わり、内蔵コマンドもパイプとリダイレクトで使えるようにする。

- **内蔵に残す**: よく使う小さなもの（`ls`, `cat`, `echo`, `cp`, `mv`, `rm`, `mkdir`, `pwd`）, シェルの状態を変えるもの（`cd`, `history`, `help`, `clear`, `term`）, カーネルの中でしかできないもの（`sync`, `reboot`, `wallpaper`, `beep`, `hwclock`, `demo`, `divzero` などの試験用）
- **アプリにする**: たまにしか使わない情報を出すもの（`hexdump`, `ps`, `mem`, `df`, `date`, `uptime`, `pci`, `net`, `arp`）。今と同じ表示にして、今あるシナリオがそのまま通るようにする
- **内蔵コマンドの出力**: 内蔵コマンドは `kprint!` をやめ、シェル用の出力マクロ（`out!`・`outln!`）で今のタスクの fd 1 に書く。fd 1 が端末なら今と同じ（画面とシリアル）。エラーは fd 2。`cat` はファイル名が無ければ fd 0 を読む
- **リダイレクトだけのとき**（`ls > A.TXT`）: シェルのスレッドの fd 0〜2 を一時的につなぎ替えて実行し、終わったら戻す
- **パイプの中のとき**（`ls | grep ELF`）: 内蔵コマンドを短い間だけのカーネルスレッドで動かす。そのスレッドの fd 0〜2 をパイプにつなぎ、ほかのコマンドと同時に動かす（同じスレッドで書く側と読む側を動かすと待ち合って止まるため）。`cd` などシェルの状態を変えるコマンドをパイプの中で使っても、シェルには効かない（Unix のシェルと同じ）
- Ctrl+C: パイプの中の内蔵コマンドのスレッドも前面の集まりに入れ、止めるよう頼まれたら途中でやめる（内蔵コマンドは読み書きのたびに確かめる）
- 足すフィルタのアプリ: `grep`（部分一致・`-i`・`-v`・`-n`）, `wc`, `head`, `tail`, `sort`, `tee`

## 5. テストの方法

- パイプと fd の表は ktest（`kernel/src/ktest.rs`）。パイプを作り、カーネルスレッド 2 本で読み書きして中身と EOF を確かめる。終わった後に参照とページが残っていないことも見る（今のプロセスのテストと同じ）
- 文法は `crates/vibe-shell` のホストのテスト
- シェルでの動きは `tests/scenarios` のシナリオ。結果はファイルに書かせて `cat` でシリアルに出すか、`wc` の数を `wait-serial` で見る
- 画面の比較は `ls | more` の 1 か所だけにする（ほかはシリアルで足りる）

## 6. オーナーに決めてほしいこと（回答済み 2026-10-12）

1. **内蔵コマンドをアプリに移すか**（§3.6）: AI の案は「出力を出すコマンドを全部アプリに移す」だった。オーナーの回答は「よく使う小規模コマンドは外に出さないほうが良い」。→ よく使う小さなものは内蔵のまま、パイプとリダイレクトで使えるようにする（D-041）
2. **アプリにするコマンドを 1 本ずつにするか、1 本にまとめるか**: 推奨どおり 1 本ずつ（D-042）
3. **読む側がいないパイプに書いたとき**（§3.2）: 推奨どおりプロセスを止める（-141）（D-042）
4. **フィルタのアプリの顔ぶれ**: 推奨どおり §3.6 の 6 本（D-042）

## 7. 心配な点

- **fd の番号の付け替え（P1）は変更の範囲が広い**: `syscall.rs` の読み書き・ソケット・`poll` がすべて「+ 3」を前提にしている。P1 では見た目の動きを変えず、今のシナリオ 54 本が通ることを先に確かめる
- **参照の数え間違い**: パイプの書く側がどこかに残ると EOF が来ず、シェルがいつまでも待つ。ktest で「全部閉じたら EOF」「プロセスが終わったら閉じる」を確かめる
- **戻らない関数**: `exit_current` は fd の表を片付けてから呼ぶ（パイプの `Arc` を持ったまま終わると、読む側に EOF が届かない。CLAUDE.md の「戻らない関数」の注意）
- **メモリ**: パイプ 1 本 4KB。8MB の `20-low-memory` でも足りる見込み

# 計画書: ユーザ空間のシェルとスクリプト

状態: **実装中**（Phase 41〜44 に割り当て。S1 完了。§6 の回答は DECISIONS.md D-042） / pipe.md の後に着手 / 作成: 2026-10-12 / 作成者: AI

シェルをカーネルからユーザ空間のアプリ `sh` に移し、変数・条件・繰り返しを持つ簡単なスクリプト言語にする。
[pipe.md](pipe.md)（パイプとリダイレクト）が済んでいることを前提にする。

## 1. 今の状態と困っていること

| 今 | 困ること |
|---|---|
| シェルは端末ごとのカーネルスレッド（`kernel/src/shell`） | シェルの不具合でカーネルが止まる。シェルを直すたびにカーネルを作り直す。「カーネルは仕組み、使い勝手はアプリ」になっていない |
| コマンドは 1 行に 1 つ。`;`・`&&`・変数・条件・繰り返しが無い | 決まった手順をまとめて実行できない |
| スクリプトのファイルを実行できない | 起動時の設定（壁紙・時刻合わせ・`httpd` の起動など）を自分で書けない |
| 終了コードは失敗したときに `[x exited with n]` と出るだけ | 結果で処理を分けられない |
| `cd` などはカーネルの関数を直接呼ぶ | アプリからはカレントディレクトリを変えられない |

## 2. ゴール

- 端末を開くと `/BIN/SH.ELF` が動く。見た目（プロンプト・行の編集・履歴・メッセージ）は今のシェルと同じ
- `;`, `&&`, `||`, 変数（`X=1`, `$X`, `$?`, `$1`）, `if`/`while`/`for`, `#` のコメントが使える
- `export X=1` で環境変数にした変数は、起動したプログラム（別の `sh` のスクリプトも）から見える
- `sh FILE.SH` でスクリプトを実行できる。`files` でダブルクリックしても実行できる
- 起動時に `/AUTORUN.SH` があれば、最初の端末がそれを実行する（§6 の 2）
- シェルが落ちてもカーネルは止まらず、その端末だけが閉じる

**やらないこと**: 関数の定義, 配列, `$(...)` の中で別のパイプを組むこと（`$(...)` 自体は §3.3 の任意）, ヒアドキュメント, ジョブ制御（`fg`・`bg`・Ctrl+Z）, POSIX sh との完全な互換

## 3. 設計の要点

### 3.1 カーネル側に足すもの

| システムコール | 中身 | 使う所 |
|---|---|---|
| `chdir(path)`, `getcwd(buf)` | 今のプロセスのカレントディレクトリ（今は `fs::chdir` をシェルのスレッドが呼んでいる） | `cd`, `pwd`, プロンプト |
| `wait_opt(pid, flags)` | `WAIT_NOHANG`（終わっていなければすぐ戻る）, `pid = -1`（どれか 1 つ） | 裏のプロセスが終わったことをプロンプトの前に出す |
| `set_foreground(&[pid], n)` | 今の端末の前面のプロセスの集まり（pipe.md §3.5 の中身をアプリから使えるように） | Ctrl+C を前面のコマンドだけに届ける |
| `reboot()`, `wallpaper(path, mode)`, `beep(freq, ms)` など | 今は内蔵コマンドがカーネルの関数を直接呼んでいるもの | カーネルの中でしかできないコマンドをアプリにする（§3.4） |

- 端末を開くとき（`gfx::console::open_terminal`）は、カーネルスレッドの代わりに `SH.ELF` を `spawn_ex` で起動する。`term_open(cmd)` は `sh -c cmd` になる
- **予備のシェル**: `SH.ELF` が無い・起動できないときだけ、今のカーネルのシェルを最小にしたもの（プログラムを起動するだけ）を動かす（§6 の 1）

### 3.2 `sh` の作り

- 文法と実行の大部分は `crates/vibe-shell`（pipe.md で作ったもの）を広げて置き、ホストの `cargo test` で確かめる。プロセスの起動・待ち・ファイルは「実行する側」の trait に分け、ホストのテストでは偽物に差し替える
- 字句 → 構文木 → 実行、の 3 つに分ける。構文木はコマンド・パイプ・`;`/`&&`/`||`・`if`/`while`/`for` の入れ子
- 行の編集は今の `kernel/src/shell/line.rs` を `crates/vibe-line` に移し、`getkey` と ANSI の出力でユーザ空間から使う。履歴は端末ごと（`sh` のプロセスごと）
- 入力が端末でないとき（`sh < FILE.SH`、`sh FILE.SH`）は、プロンプトを出さずに 1 行ずつ読む
- Ctrl+C: `sh` は `ctrl_c(CATCH)` で自分では止まらない。前面のコマンドだけが止まる。入力の途中なら行を取り消す（今と同じ）

### 3.3 言語

| 書き方 | 意味 |
|---|---|
| `a ; b`, 改行 | 順に実行 |
| `a && b`, `a \|\| b` | 終了コードで続けるか決める |
| `X=値`, `$X`, `${X}`, `$?`, `$#`, `$1`〜`$9`, `$@` | 変数、最後の終了コード、スクリプトの引数 |
| `export X`, `export X=値`, `X=値 cmd` | 環境変数にする（起動するプログラムに渡る）。`X=値 cmd` はそのコマンドにだけ渡す |
| `'...'`, `"..."`（中で `$X` を展開）, `\` | 引用 |
| `if 条件; then …; elif …; else …; fi` | 条件は「コマンドの終了コードが 0」 |
| `while 条件; do …; done`, `for x in a b c; do …; done` | 繰り返し。`break`, `continue` |
| `*.TXT` | ファイル名の展開（カレントディレクトリの中だけ、`*` と `?`） |
| `$((式))` | 整数の算術（`+ - * / %`、比較、括弧） |
| `# …` | コメント |
| `$(cmd)`（任意） | コマンドの出力に置き換える。パイプがあればできる |

- 内蔵コマンド（`sh` の中で動く）: `cd`, `pwd`, `exit`, `history`, `help`, `echo`, `test` / `[`（`-e`・`-d`・`=`・`!=`・`-eq`・`-lt` など）, `set`（変数の一覧）, `export`, `unset`, `env`（環境変数の一覧）, `.`（今のシェルでスクリプトを読む）, `true`, `false`, `sleep`
- 1 行の長さ・入れ子の深さ・繰り返しの数に上限は設けないが、Ctrl+C で止められることを確かめる

### 3.4 カーネルの内蔵コマンドを片付ける

pipe.md §3.6 で、情報を出すたまにしか使わないコマンドはアプリになっている。よく使う小さなコマンドは、`sh` の内蔵コマンドとして残す（D-041。カーネルの内蔵から `sh` の内蔵へ移るだけで、アプリにはしない）。

| コマンド | 行き先 |
|---|---|
| `ls`, `cat`, `echo`, `cp`, `mv`, `rm`, `mkdir`, `pwd`, `cd`, `history`, `help`, `clear`, `sleep`, `sync` | `sh` の内蔵コマンド（今のシステムコールで書ける。`clear` は `ESC [ 2 J` を書くだけ） |
| `term` | `sh` の内蔵（`term_open` を呼ぶだけ） |
| `write`, `append` | `echo … >` / `>>` で置き換えられるので消す（シナリオで使っていれば書き換える） |
| `reboot`, `wallpaper`, `beep`, `hwclock`, `demo` | §3.1 のシステムコールを足してアプリに |
| `divzero`, `nullptr`, `overflow`, `panic` | カーネルの例外の試験用（シナリオ `04-divzero-panic`・`06-page-fault`・`07-stack-overflow` が使う）。テスト用ビルドだけのシステムコールにして `fault` アプリから呼ぶ（D-042） |

`sh` の内蔵コマンドの入出力:
- リダイレクトだけのとき: `dup2` で自分の fd 0〜2 をつなぎ替えて実行し、終わったら戻す
- パイプの中のとき: `fork` が無いので、そのコマンドだけを子の `sh -c '…'` として起動する（パイプの中では `sh` の読み込みの分だけ遅くなる）。パイプの外では今のプロセスの中で動く

## 5. テストの方法

- 言語のほとんどは `crates/vibe-shell` のホストのテスト（プロセスの起動を偽物にして、「どのコマンドがどの引数・どの入出力で呼ばれたか」と終了コードを確かめる）
- QEMU のシナリオは「スクリプトを流して結果をシリアルで見る」形を中心にする。スクリプトは `tests/` の下に置き、Makefile のテスト用イメージに入れる
- S1 では、今の 54 本のシナリオが **変えずに** 通ることを完了条件にする。画面の比較の期待画像が変わる場合は、違いを目で確かめてから作り直す

## 6. オーナーに決めてほしいこと（回答済み 2026-10-12。D-042）

1. **予備のシェルを残すか**（§3.1）: 推奨どおり残す（プログラムを起動するだけの数十行）
2. **起動時のスクリプトの名前と場所**: 推奨どおり `/AUTORUN.SH`
3. **カーネルの例外の試験用コマンド**（§3.4）: 推奨どおりテスト用ビルドだけのシステムコールにして、`fault` アプリから呼ぶ
4. **言語の範囲**（§3.3）: 推奨どおり §3.3 の表 + 算術 `$((…))`（整数の四則・剰余・比較）を入れる。関数・配列は入れない

## 7. 心配な点

- **見た目を今と同じにする**: プロンプトの色・メッセージの文言・行の編集の細かい動き（行をまたぐ左右移動など）が、画面の比較のシナリオに写っている。`line.rs` はそのまま移し、文言は今の `shell/mod.rs` から写す
- **端末を開く速さ**: 今はスレッドを作るだけだが、`SH.ELF` を読んで gzip を展開する分だけ遅くなる（アプリの起動と同じ。数十 ms の見込み）
- **メモリ**: 端末 1 つにつき `sh` のプロセスが 1 つ（スタック 64KB + ヒープ）。端末を 10 個開いても 1MB 程度。8MB の `20-low-memory` で確かめる
- **ユーザ空間で行の編集**: 今の `LineEditor` はカーネルの `gui::read_key` を直接呼ぶ。ユーザ空間では `getkey` の 1 キーごとにシステムコールになるが、キー入力の速さなら問題にならない

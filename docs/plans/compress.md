# 計画書: カーネルの圧縮（LZSA の組み込み）

状態: **完了（2026-10-12。結果は §9）。PLAN.md の Phase 27〜29** / 作成: 2026-10-12 / 作成者: AI / 方式の決定: オーナー（2026-10-12, DECISIONS.md D-034）

自作した LZSA（[計画書](lzsa.md), DECISIONS.md D-033）を使い、フロッピーの上のカーネル（`KERNEL.SYS`）を圧縮して置き、ローダが展開する。オーナーの最初の希望は「カーネルは展開の簡単さを優先」。

**スコープ**: この計画はカーネルだけ。アプリの圧縮はオーナーの指示（2026-10-12）で別に考える（§8）。

## 1. 今の状態と測定（2026-10-12）

| 今 | 困ること |
|---|---|
| ローダは `KERNEL.SYS` を RAM ディスクから `0x100000` へそのまま写す | フロッピーの約 2 割（308KB）をカーネルが使う |
| フロッピーの空きは約 648KB | ネットワーク・デスクトップの計画でアプリやデータが増える |
| ローダは起動のたびにフロッピー全体（1.44MB）を読む | 圧縮しても起動は速くならない（読む量が変わらない）。この計画の効き目は空きが増えることだけ |

自作の `vibe-lzsa`（既定の設定）で測った kernel.sys の大きさ:

| 形式 | 大きさ | 元との比 |
|---|---|---|
| 元 | 308,528 | 100% |
| LZSA1（本家の値。自作は 100.11%） | 約 160,000 | 約 52% |
| LZSA2 | 142,544 | 46.2% |
| LZSA2 + BCJ（§3.3） | 135,129 | 43.8%（BCJ で −5.2%） |

- 本家の `lzsa` で測ったときの BCJ の効き目（lzsa.md §1）: LZSA1 で −6.0%、LZSA2 で −5.2%
- カーネルを圧縮すると、フロッピーの空きは約 648KB → 約 820KB になる見込み

## 2. ゴール

- `KERNEL.SYS` は LZSA2 + BCJ で圧縮した形で置き、ローダが unreal モードのままアセンブラの展開ルーチンで `0x100000` に展開する。展開した後のカーネルの配置・入口・ブート情報は今と同じ
- 圧縮していない `KERNEL.SYS` も今どおり起動する（先頭の印で見分ける。§6）
- 壊れた圧縮ファイルでは、ローダは理由を表示して止まる

**やらないこと**:
- アプリ（`/BIN/*.ELF`）の圧縮、ELF ローダでの展開、共有の辞書（別の計画で考える。§8）
- 起動を速くすること（ローダが使っているクラスタだけを読むようにする変更。§8）
- ファイルシステムでの透過的な圧縮
- 展開にかかる時間の測定・上限（オーナーの判断で外した。起動全体に比べて小さく、測る意味が薄い。§6）
- LZSA2 以外の形式（LZSA1・LZ4・ZX0・deflate など）
- 圧縮器を OS の中で動かすこと（圧縮はホストのビルドの時だけ）

## 3. 設計の要点

### 3.1 カーネルをどこで展開するか（決定: A）

オーナーが A（ローダの中、アセンブラ）を選んだ（D-034）。検討した 2 つ:

| | A: ローダ（`boot/loader.asm`）で展開 **【採用】** | B: カーネルの前に付けた小さな Rust の展開部（Linux の bzImage と同じ考え） |
|---|---|---|
| 流れ | ローダが圧縮した `KERNEL.SYS` を作業用の場所へ写す → unreal モードのまま手書きの x86 の展開ルーチンで `0x100000` へ展開 → BCJ を戻す → CRC32 を確かめる → 今どおりプロテクトモードへ移ってジャンプ | `KERNEL.SYS` = 展開部 + 圧縮したカーネル。ローダは今どおり `0x100000` に写してジャンプ。展開部が自分と圧縮データをカーネルの終わりより後ろへ移し、`vibe-lzsa` の展開器で `0x100000` へ展開してカーネルへ跳ぶ |
| 良い所 | 段階が増えない。カーネルのリンクのしかた・入口・`BootInfo` の意味が変わらない。「ローダがカーネルを読み込む」という今の説明のまま | 展開器の正しさをホストで確かめられる。ローダを変えなくてよい |
| 悪い所 | アセンブラの展開ルーチンはホストで `cargo test` できない（§5.3 で補う）。16 ビットのコードで 32 ビットの番地（`a32`/`o32` の接頭辞）を使うので読みにくい | 起動の段階・クレート・リンカスクリプト・自分を移すアセンブラが増える。移した先が重ならないことをビルド時に確かめる仕組みが要る |

展開ルーチンは NASM で新しく書く。LZSA2 で約 200 バイト + フレーム・BCJ・CRC32 で合わせて 400〜500 バイトの見込み。

### 3.2 メモリの置き場所

```
0x00100000 ─ 展開先（カーネルの .text〜.data。.bss はカーネルが 0 にする）。今と同じ
     …       上限は KERNEL_MAX（RAMDISK_ADDR まで）。展開前にヘッダの大きさで確かめる
0x00400000 ─ RAM ディスク（フロッピー全体）。今と同じ
0x00568000 ─ RAM ディスクの終わり
0x00570000 ─ 作業用の場所: 圧縮した KERNEL.SYS をクラスタをたどって続けて写す（約 135KB）。
             その後ろに CRC32 の表（1KB）
```

- 圧縮したファイルは RAM ディスクの中でとびとびのクラスタに置かれうるので、今の `load_kernel` と同じくクラスタをたどって作業用の場所へ続けて写し、そこから展開する（展開ルーチンは入力を前から順に読むだけにして単純にする）
- 作業用の場所は RAM ディスクの終わりを 64KB に切り上げた所。`check_memory_fits` の「1 つの使用可能領域に収まるか」の終わりを、RAM ディスクの終わりから作業用の場所の終わりに広げて E820 で確かめる（約 5.4MB → 約 5.6MB。最低動作メモリ 8MB には収まる）
- 展開先 `[0x100000, 0x400000)` と作業用の場所は重ならない（番地の決め方で保証する）。展開ルーチンは書く前に出力の上限（`RAMDISK_ADDR`）を越えないか毎回確かめ、越えたら壊れたファイルとして止まる（壊れたデータで RAM ディスクやローダを上書きしないため）
- 作業用の場所は起動後は使わない。カーネルの物理メモリ管理は今どおりカーネルと RAM ディスクだけを予約するので、自然に空きになる
- 他の案: 640KB の下（`0x20000`〜`0x7FFFF`、約 384KB）に置くと高い所の必要量は増えないが、圧縮後のカーネルの上限がそこで決まり、EBDA の位置にも左右されるので採らない

### 3.3 x86 の BCJ フィルタ（決定: カーネルだけに使う）

- `call`（`E8`）・`jmp`（`E9`）の後ろの相対番地を、圧縮の前に絶対番地へ直す。同じ関数を呼ぶ命令が同じバイト列になり、一致が増える。展開した後に逆の変換で戻す
- 決まりは xz の x86 フィルタと同じ考えで自分で書く: 相対番地の上位 1 バイトが `00` か `FF` のときだけ直し、結果は 25 ビットで符号を広げて上位 1 バイトを `00`/`FF` に保つ（戻す側も同じ位置で同じ判断ができる）。直したら 5 バイト進める
- 番地の基準はカーネルが置かれる `0x100000`（ヘッダに持つ）
- 戻す処理はアセンブラで 40 バイト前後。ホスト側（圧縮）と Rust 側（カーネルの自己確認、§5.2）は `crates/` に置いてホストで往復を確かめる

### 3.4 圧縮したファイルの形

先頭に小さなヘッダを付け、後ろに LZSA2 のストリーム形式（64KB ごとのフレーム）を置く。カーネルは 64KB を超えるので raw block は使えない。ストリーム形式は元の大きさを持たないので、展開前に上限を確かめるためにヘッダに持たせる。

| オフセット | 大きさ | 中身 |
|---|---|---|
| 0 | 4 | 印 `"VPK1"`（LZSA の `7B 9E` とも、今のカーネルの先頭の命令とも違う） |
| 4 | 1 | 形式（2 = LZSA2。ほかの値は壊れたファイルとして扱う） |
| 5 | 1 | フラグ（bit0 = BCJ） |
| 6 | 2 | ヘッダの大きさ（後で欄を足しても読み飛ばせるように） |
| 8 | 4 | 展開後の大きさ |
| 12 | 4 | BCJ の基準の番地 |
| 16 | 4 | 展開後の中身の CRC32 |
| 20〜 | | LZSA2 のストリーム（3 バイトのヘッダ + フレーム） |

- CRC32 はローダで確かめる（§6）。壊れたフロッピーで変なカーネルに跳ぶのを防ぐ。ビットごとの計算は 1 バイトに 35 命令ほどかかり 486DX-33 で 300KB に 0.5 秒を超える見込みなので、256 項目の表（1KB）を作業用の場所に作ってから計算する（コード 50 バイト前後、1 バイトに 6 命令ほど）
- ヘッダの読み書き・BCJ・CRC32 は新しいクレート `crates/vibe-pack`（`no_std`。作る側は `alloc` の feature）に置く。`vibe-lzsa` は LZSA の形式だけに保つ。アプリの圧縮を後で考えるときもこの形を使い回せる
- ホストのコマンドは `tools/vibe-lzsa` に `pack -f2 [--bcj BASE] IN OUT` と `unpack` を足す
- ブート情報の `kernel_size` には展開後の大きさを入れる（今の「メモリ上の大きさ」という意味を保つ）。圧縮したファイルの大きさが要るなら欄を足す（NASM と Rust の両方の定義を同時に変える）

### 3.5 ビルド

- `build/kernel.sys`（今の平らなバイナリ）→ `build/kernel.vpk`（`vibe-lzsa pack -f2 --bcj 0x100000`）を作り、イメージには後者を `KERNEL.SYS` として入れる。テスト用イメージも同じ
- `make COMPRESS=0` で今どおり圧縮しないイメージも作れるようにする（§6）
- `make size-report`: 元の大きさ・圧縮後・比と、フロッピーの空きを表にする

## 5. テストの方法

### 5.1 ホスト

- `crates/vibe-pack` の `cargo test`（K1 の完了条件）
- `make test-lzsa` に kernel.sys の pack → unpack の往復を足す
- 本家の `lzsa` は使わない（D-033 の「最終のテストは本家に依存しない」を守る）

### 5.2 QEMU のシナリオとカーネル内テスト

1. **カーネルの自己確認（ktest）**: カーネルが `/KERNEL.SYS` を読み、Rust の展開器と BCJ の逆変換で展開して、メモリ上の自分の `.text`・`.rodata` と比べる（`.data` は動いている間に変わるので比べない。リンカスクリプトに `.rodata` の終わりの記号を足す）。ローダの展開ルーチンの結果を、ホストで確かめた Rust の展開器と毎回突き合わせることになる
2. **圧縮していないカーネル**: `COMPRESS=0` で作ったカーネルを入れたイメージ（`build/vibeos-raw.img`、`31-loader-fragmented` のイメージと同じ作り方）で `01-loader` 相当が通る
3. **壊れたカーネル**: 圧縮したデータの途中のバイトを書き換えたイメージで、ローダが理由を表示して止まり、`VibeOS kernel starting` が出ない（`21-too-little-memory` と同じ形）
4. **メモリ**: `20-low-memory`（8MB）は作業用の場所を足しても通る。`21-too-little-memory`（5MB）は今どおりローダが止まる
5. **Bochs**: `make test-bochs` は同じシナリオを流すので、圧縮したカーネルの起動も Bochs で確かめられる（Pentium II 相当。486 そのものではない）
6. **大きさ**: `make test` の中で、イメージの `KERNEL.SYS` の先頭が `VPK1`（`COMPRESS=0` のときを除く）で、元より小さいことを確かめる。`make size-report` の表を LOG.md に残す

### 5.3 アセンブラの展開ルーチンを確かめる（K3）

- 展開ルーチンを `boot/unlzsa2.inc` に分け、32 ビットのレジスタと番地だけを使って書く。`bits 16` で include すれば unreal モード用（NASM が `66`/`67` の接頭辞を付ける）、`bits 32` なら 32 ビット用になり、どちらも同じ動きになる
- テスト用カーネル（`qemu-test` の feature）のときだけ、`kernel/build.rs` で `nasm -f elf32` で組んだ 32 ビット版をリンクする
- 同じく `build.rs`（ホストで動く）で `vibe-lzsa` の境目のデータ（`samples`）を圧縮して埋め込み、ktest でアセンブラの展開ルーチンに展開させて元と比べる
- これで「今のカーネルでは通らない分かれ道」（長い長さの拡張、遠いオフセット、フレームの境目など）も毎回確かめられる

## 6. オーナーが決めたこと（2026-10-12, DECISIONS.md D-034）

- 展開はローダの中でアセンブラ（A）、形式は LZSA2、BCJ はカーネルだけ、この計画はカーネルだけ（アプリは別に考える）
- 展開にかかる時間は測らない・上限も設けない（「時間測る意味があまりないと思うので削除」。最初の案の K4 を外した）
- 圧縮しない道を残す（`make COMPRESS=0`、ローダは印の無い `KERNEL.SYS` を今どおり写す）。切り分けに使え、ローダの増える分は数バイト
- ローダで CRC32 を確かめる（コード 50 バイト前後・1KB の表）。壊れたフロッピーで変なカーネルに跳ぶのを防ぐ

## 7. 心配な点

- **アセンブラの展開ルーチンの誤り**: 境目の扱いを間違えても今のカーネルでたまたま通ることがある。K3 の境目のデータのテストで補う。K3 を省くと、カーネルが変わったときに初めて起動しなくなることがある（それでも `make test` で気づける）
- **unreal モードと BIOS**: 展開は `load_kernel` の中で BIOS を呼ばずに行い、直前に `enter_unreal` に入り直す。画面モードを決める `choose_video`（VESA の BIOS を呼ぶ）は今どおり展開の後
- **ローダの大きさ**: 今 3,952 バイト（上限 32,256）。400〜500 バイト増えても十分収まる
- **起動は速くならない**: ローダがフロッピー全体を読む作りのまま（§8）
- **カーネルの `.data` の大きさの注意**（CLAUDE.md）は、圧縮すると 0 は縮むのでフロッピーへの影響は小さくなる。ただし展開後の大きさとメモリの使い方は変わらないので、今の注意はそのまま残す

## 8. 別の計画の候補（この計画には入れない）

### 8.1 アプリの圧縮（オーナーの指示で別に考える）

最初の案で検討した内容と測定を、後で計画を作るときのために残す。

- 測定（自作の LZSA2）: アプリ 16 本は 1 本ずつの合計で 372,352 → 161,780。BCJ を足しても −2.1% しか縮まない。`HELLO.ELF` を共有の辞書にした見積もりでは、ほかの 15 本が 157,229 → 約 105,600（−33%。辞書そのものは圧縮して約 4.5KB 別に要る）。カーネルと合わせると空きは約 1,030KB になる見込み
- 考えた形: §3.4 の `VPK1` のヘッダを使い、`process::spawn` が先頭の印を見て `vibe-lzsa` の `no_std` の展開器で展開してから ELF として読む。名前は `.ELF` のまま（拡張子を変える案もある）。壊れていれば `ENOEXEC`
- 共有の辞書: `vibe-rt` の共通部分を辞書（例: `/BIN/APPS.DIC`）として 1 つ置き、各アプリはその続きとして圧縮する。展開器の `decompress_block(…, out, start, …)` は `out[..start]` を参照できるので、辞書を先頭に写せば展開できる。辞書を消すと全部のアプリが動かなくなる・辞書の ID を確かめる必要がある、という弱さがある

### 8.2 起動を速くする

ローダはフロッピー全体を RAM ディスクに読むので、圧縮しても起動の時間は変わらない。使っているクラスタだけを読む・カーネルを先に読んで残りは後から読む、といった変更をすれば、圧縮が起動の速さにも効く。

## 9. 結果（2026-10-12）

| | 元 | 圧縮後 | 比 |
|---|---|---|---|
| KERNEL.SYS | 308,528 | 135,173 | 43.8% |
| テスト用カーネル（ktest のデータ込み） | 621,600 | 344,220 | 55.4% |
| フロッピーの空き | 約 645KB | 819,200 | |
| ローダ（loader.bin） | 3,952 | 5,232 | +1,280 バイト |

- 既存のシナリオと新しいシナリオ（`42-kernel-uncompressed`・`43-kernel-broken`）がすべて通った。ktest で、ローダが置いたカーネルの `.text`・`.rodata` が KERNEL.SYS を Rust で展開したものと一致し、アセンブラの展開ルーチンが境目のデータ（ホストで圧縮した 300 個あまり）をすべて元どおりに展開し、壊れたデータで出力の上限を越えて書かないことを確かめた
- ローダの増え方は見込み（400〜500 バイト）より大きかった。unreal モードの 16 ビットのコードで 32 ビットの番地を使うと、ほぼすべての命令に 66/67 の接頭辞が付くため。上限（32,256）にはまだ十分余裕がある
- BCJ の決まりを 1 つ足した（§3.3 の「同じ位置で同じ判断ができる」が最初の書き方では成り立たなかった）: 直さなかった E8/E9 の 1〜3 バイト後から書き換えると、その E8/E9 の判断に使った 4 バイト後のバイトが変わり、戻す側が違う判断をする。直さなかった E8/E9 の 4 バイト後より前から始まる書き換えはしないことにした（ホストのテストで E8/E9 と 00/FF だらけのデータを往復させて見つけた）
- テスト用カーネルには NASM で組んだオブジェクト（`boot/unlzsa2_test.asm`）をリンクしている（`kernel/build.rs`、`qemu-test` のときだけ）。ローダと同じ展開ルーチンをそのまま確かめるため

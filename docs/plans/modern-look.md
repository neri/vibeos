# 計画書: デスクトップの見た目を今風にする

状態: **実装中**（M1〜M4 完了。M3 と M4 の分け方を変えた: D-049。§6 の回答は DECISIONS.md D-047・D-048） / ブランチ `modern-look` で作業し、main に合流するかは未定（D-046） / 作成: 2026-10-13 / 作成者: AI

デスクトップの見た目を、今の「Windows 3.x 風・8x8 の太い文字・16 色」から、フルカラー・なめらかな文字・角の丸いウィンドウと影のある今風のものにする。
仕組み（ウィンドウ・端末・アプリ・システムコールの考え方）はそのままにし、描き方と色の扱いを変える。

画面は 2 つのモードになる:

| モード | 画面 | 中身 |
|---|---|---|
| **モダン** | 32 ビットの直接色の VESA モードのうち、メモリとモニタに合う一番大きいもの（§3.1） | この計画で作る今風のデスクトップ |
| **レトロ** | 320x200・モード 13h（今の全画面モードそのまま） | 32 ビットのモードが無いとき・`video=320x200`・起動時に Shift |

今の「640x480・8 ビットのデスクトップ」は無くす（32 ビットのモードが無ければレトロになる）。

## 1. 今の状態と困っていること

| 今 | 困ること |
|---|---|
| 画面は 1 ピクセル 8 ビット（パレット 256 色）。重ね合わせもアプリのバッファも 8 ビット | 半透明・影・文字のなめらかな縁・グラデーションが描けない。24 ビットの BMP は誤差拡散で荒れる |
| 画面は 640x480 まで（`vga.rs` の `MAX_WIDTH`・`MAX_HEIGHT`） | 今のパソコンやエミュレータの画面では狭い |
| 文字は 8x8 の固定幅のビットマップ（`font8x8`）だけ | 小さく太く、いかにも古い。字の幅がそろっているので UI の文字がまばら |
| 部品（`vibe-ui`）は灰色の地に白と濃い灰色の縁の立体 | 見た目が 1990 年頃。マウスを乗せたときの変化（ホバー）が無い |
| ウィンドウは 1 ピクセルの枠・青い 12 ピクセルのタイトルバー・文字の [_] [x] | 四角くて平たく、どれが手前か分かりにくい |
| バー・メニューは文字だけ。アイコンが無い | 何のアプリか一目で分からない |
| マウスカーソルは 2 色 | 縁がギザギザ |

（今の画面: `docs/images/desktop.png`）

## 2. ゴール

- モダンモードは 1 ピクセル 32 ビット（フルカラー）だけを扱う。画面は使える 32 ビットのモードのうち、メモリとモニタに合う一番大きいものを選ぶ（640x480〜2560x1600）
- UI の文字は字の幅が字ごとに違う（プロポーショナル）なめらかなフォント、端末は読みやすい固定幅のフォント（8x16 前後）
- ウィンドウは角が丸く、影があり、手前のものがはっきり分かる。タイトルバーのボタンはアイコンで、マウスを乗せると色が変わる
- バー・メニュー・ファイルマネージャにアイコンが出る
- 部品は平らな今風の見た目（角の丸いボタン・ホバー・強調色のフォーカスの輪・細いスクロールバー）
- 既定の背景はグラデーション。24 ビットの BMP を背景や `view` でそのまま（誤差拡散せずに）出せる
- 今あるアプリは、作り直さなくても今までどおり動く（8 ビットのウィンドウはそのまま使える）
- レトロモード（320x200）は今のまま動き続ける

**やらないこと**:
- 32 ビット以外（24/16/15/8 ビット）の VESA モードへの対応
- レトロモードの見た目の変更
- アニメーション（ウィンドウが開くときの拡大など）、ウィンドウ全体の半透明、ぼかし（すりガラス）。486 では重すぎる
- 画面の拡大（HiDPI）。文字や部品はピクセルの大きさが決まっている
- 日本語の表示（別の計画。ただしフォントの形式は全角を足せるようにしておく）
- 動いている間の画面モードの切り替え（今までどおり BIOS が要るため）

## 3. 設計の要点

### 3.1 画面のモードと色の扱い（いちばん土台になる変更）

- **ローダ**: VESA のモード一覧から「32 ビット・直接色（メモリモデル 6）・リニアフレームバッファ」のモードを探し、次の上限をすべて満たす中で一番大きい（幅 × 高さが最大の）ものを選ぶ。見つからなければモード 13h（レトロ）
  - **メモリ**: 画面 1 枚（幅 × 高さ × 4 バイト）が E820 で分かる RAM の 1/8 以下。ただし 640x480 はいつも使ってよい（最低の 8MB でもモダンになるように）。画面と同じ大きさのもの（裏のバッファ・背景の画像・端末などのウィンドウ）が 3〜4 枚分要るので、1/8 なら半分以上が残る

    | メモリ | 上限の目安（実際はモード一覧にあるもののうち、1/8 に収まる一番大きいもの） | 画面 1 枚 |
    |---|---|---|
    | 8〜15MB | 640x480 | 1.2MB |
    | 16〜31MB | 800x600 | 1.9MB |
    | 32〜63MB（QEMU の標準） | 1280x800（QEMU のモード一覧で） | 4.1MB |
    | 64〜127MB | 1280x1024 | 5.2MB |
    | 128〜255MB | 1920x1200 | 9.2MB |
    | 256MB〜 | 2560x1600 | 16.4MB |

  - **モニタ**: VESA の一覧はビデオカードが出せるモードで、モニタが映せるとは限らない（映せないモードを選ぶと真っ黒になる）。VBE の DDC（`int 10h` の `4F15h`）で EDID を読み、モニタの本来の解像度（詳細タイミングの 1 つ目）を超えるモードは選ばない。EDID が読めなければ 1024x768 まで
  - **フレームバッファの窓**: カーネル空間の最後の 16MB に対応付けている（DESIGN.md §8.0）ので、1 行のバイト数 × 高さが 16MB 以下（2560x1600 が収まる）
  - `BOOT.CFG` の `video=WxH` で上限を指定できる（メモリとモニタの上限より優先する。EDID が読めない大きなモニタで大きくする・テストで画面の大きさを固定するのに使う）。`video=320x200` と起動時の Shift はレトロ（大きすぎて映らないときの逃げ道）
  - 32 ビットの中の R・G・B の位置はモード情報のマスクで確かめ、ふつうの XRGB8888（B が下位）以外は選ばない
  - 選んだモードと、そう決めた理由（メモリ・EDID・`video=`）をシリアルに出す
- **ブート情報**: 1 ピクセルのビット数（8 か 32）を足す（`bootinfo.inc` と `bootinfo.rs`）。カーネルはこれでモダン（デスクトップ）かレトロ（全画面）かを決める
- **画面の大きさを決め打ちしない**: `vga.rs` の `MAX_WIDTH`・`MAX_HEIGHT` と、それを使う静的なバッファをやめ、ブート情報の大きさでヒープから取る。最初の端末の位置・新しいウィンドウを置く位置・バーの幅も画面の大きさから決める
- **重ね合わせ**: モダンでは `gui` の行のバッファ・背景・バー・メニュー・カーソルを 32 ビット（XRGB8888）で描き、そのまま VRAM に書く。レトロは今までどおり 8 ビット。書き換えた行だけ送る仕組みは変わらない
- **8 ビットのウィンドウ**（今のアプリ・レトロのための古いバッファ）: 重ね合わせるときに「パレット番号 → 32 ビットの色」の表（256 個の u32）で直す。独自のパレットを持つウィンドウもその表を差し替えるだけになる（今の「近い色への置き換え」が要らなくなる）
- 6 ビットの DAC の値を 8 ビットに広げる式は QEMU の画面取得と同じにする（M1 で今の期待画像がそのまま通るように）

### 3.2 描画のライブラリ（`crates/vibe-gfx`）

- 32 ビットの `Canvas`（`&mut [u32]`・幅・高さ）を足す。8 ビットの `Surface` は残す（今のアプリとレトロのため）
- 基本: 点・矩形・線・画像の転送に加え、
  - **アルファ合成**: 整数だけ（`(src*a + dst*(255-a)) / 255` を掛け算とシフトで）。FPU は使わない
  - **角の丸い矩形**: 角の 1/4 円の「覆う割合」の表を半径ごとに先に作り、縁だけ混ぜる（中は普通の塗り）
  - **影**: ぼかした角と辺の濃さの表を先に作り、ウィンドウの外側の縁だけに重ねる（ウィンドウの中身の下は描かない）
  - **グラデーション**: 縦・横の 2 色（行ごと・列ごとに色を計算）
  - **アルファ付きの画像**（アイコン・カーソル）: 事前に掛けたアルファ（premultiplied）の ARGB
  - **32 → 8 ビット**: 標準のパレットの近い色へ（レトロで 32 ビットのウィンドウを出すとき）
- 重い処理は「縁だけ」「先に計算した表」で済ませ、ピクセルごとの合成を画面全体には行わない
- 中身はホストの `cargo test` で、決まった入力から決まったピクセルが出ることを確かめる

### 3.3 フォント（`crates/vibe-font`, `tools/vibe-fontgen`）

- **ホストで先にラスタライズする**: TrueType のフォントを、ホスト側のツール `tools/vibe-fontgen`（外部クレートの `fontdue` などを使ってよい。ホストのツールなので）で決まった大きさのビットマップにし、独自の形式（`.VFN`）でフロッピーに入れる
  - 形式: 見出し（大きさ・行の高さ・ベースライン）、字ごとの送り幅・位置・幅・高さ、1 ピクセル 4 ビットの濃さ（16 段階）
  - 文字の範囲は ASCII から始め、後で全角を足せるよう「文字コード → 字」の表は疎にしておく
- **入れるフォント**（D-047。許諾は SIL Open Font License を認めた）: UI 用のプロポーショナルは Inter か Noto Sans（本文 1 つと太字か大きめの見出し 1 つ）、端末用の固定幅は JetBrains Mono か Noto Sans Mono。いくつかの大きさを画像にしてオーナーに見てもらってから決める
- **描画は自作**: 濃さをアルファにして `Canvas` に合成する（`Font::draw` / 文字列の幅を測る `measure`）
- **置き場所**: `/SYSTEM/FONTS/*.VFN`（いつも gzip。§3.9）。カーネルは起動時に読み込む（無ければ今の 8x8 で動く）。アプリは `vibe-rt` が最初に使うときにファイルを読む（ヒープに 20KB 前後）
- **端末**: モダンでは固定幅のフォントで描く。格子の大きさは端末のフォントから取る（今も「1 文字の幅はフォントから取る」になっている）。既定は 80 桁 × 25 行（8x16 なら 640x400）。画面が 640x480 のときは入る大きさに縮める。ANSI の 16 色は今風の配色（暗すぎない青など）に変える。レトロでは今の 8x8・40 桁のまま

### 3.4 見た目（テーマ）

- 色・半径・影の大きさ・余白は 1 か所（`crates/vibe-theme` か `vibe-ui::theme`）にまとめ、カーネルの `gui` とアプリの `vibe-ui` が同じものを使う
- 方向（D-047）: 今の配置（上端のバー + メニュー）のまま、
  - 明るい地（白〜薄い灰色）に強調色 1 色（青）。文字は黒ではなく濃い灰色
  - **ウィンドウ**: 角の半径 6〜8、影、1 ピクセルの薄い縁。タイトルバーは中身と同じ地の色で高さ 24 前後、題名は UI のフォント。手前のウィンドウは影を濃く、奥のウィンドウは題名を薄く
  - **タイトルバーのボタン**: 最小化・閉じるをアイコンで。マウスを乗せると地の色が付く（閉じるは赤）
  - **上端のバー**: 高さ 24 前後、半透明風の白（実際は背景との合成を先に計算した色）。左に「VibeOS」のロゴとメニュー、ウィンドウのボタンはアイコン + 題名、右に状態
  - **メニュー**: 角の丸いパネルと影、項目はアイコン + 名前、乗せた項目を強調色で
  - **マウスカーソル**: アルファ付きの矢印（白に黒い縁・小さな影）
  - **背景**: 既定は 2 色のグラデーション（起動時に計算。ファイルは要らない）
- 今の 640x480 のクラシックの見た目は選べるようにしない（D-047）。古い見た目はレトロモードとして残る

### 3.5 アイコン（`tools/vibe-icongen`）

- 16x16 と 32x32 の ARGB。元の絵は AI が SVG を手で書き（D-047）、ホストのツールで PNG にしてから独自の形式（`.VIC`、事前に掛けたアルファ、ランレングスで縮める）にしてフロッピーに入れる
- 置き場所: `/SYSTEM/ICONS/`（いつも gzip。§3.9）。アプリのアイコンは `アプリ名.VIC`（無ければ汎用のアイコン）。ファイルの種類（フォルダ・テキスト・画像・スクリプト・実行ファイル）も

### 3.6 ウィンドウとアプリの API

- `win_open` のフラグに「中身は 32 ビット」を足す（`WIN_RGB32`）。`win_blit` は幅 × 高さ × 4 バイトを読む。フラグが無ければ今までどおり 8 ビット
- `vibe-rt::gfx::Window` に 32 ビットのバッファ（`Canvas`）を持つ版を足す
- 画面の大きさとモード（モダン/レトロ）は今の `sys_info` で分かる。アプリは画面より大きいウィンドウを開かない
- **ホバーのためのマウスの移動**: ボタンを押していない移動もウィンドウに届くか確かめ、届かなければ送る（間引いて、キューを溢れさせない）。ウィンドウからマウスが出たことも知らせる
- **レトロで 32 ビットのウィンドウを開いたとき**: カーネルが標準のパレットの近い色に直して出す（動くが色は落ちる。320x200 より大きいウィンドウは今までどおり左上だけ見える）。アプリ側に 8 ビットの描き方を 2 通り持たせない

### 3.7 部品のライブラリ（`vibe-ui`）

- 描画を 32 ビットの `Canvas` とテーマの色に移す（入力と状態の変化の部分は今のまま。ホストのテストもそのまま使える）
- ボタン（角の丸い平らな地、ホバー・押下・既定のボタンは強調色）、テキスト欄（薄い枠、フォーカスで強調色の輪）、一覧（行の高さを広げ、選んだ行は角の丸い強調色、アイコンを出せる）、細いスクロールバー、チェックボックス（強調色の地に白いチェック）、ダイアログ（角の丸いパネル）
- 文字の配置は `measure` で幅を測ってから（プロポーショナルなので「文字数 × 8」で計算しない）

### 3.8 速さとメモリ

| 画面 | 裏のバッファ（32 ビット） |
|---|---|
| 640x480 | 1.2MB |
| 800x600 | 1.9MB |
| 1024x768（QEMU の標準の 32MB） | 3.0MB |
| 1280x1024 | 5.2MB |
| 1920x1200 | 9.2MB |
| 2560x1600 | 16.4MB |

- **486 での速さ**: 1024x768 の画面全体の書き直しは 3MB。書き換えた範囲だけ重ね合わせて送る今の仕組みを守り、合成は縁・文字・アイコン・カーソルだけにする。影と角の表はウィンドウの大きさが変わらない限り作り直さない
  - 速さの目安を自動で見る: テスト用のビルドで「画面全体の重ね合わせ 1 回」「ウィンドウを 1 ピクセル動かしたときの書き直し」の時間を PIT の刻みで測ってシリアルに出し、QEMU で上限を見る（遅くなったことに気づくため。実機の速さの保証ではない）
- **メモリ**: 32 ビットのウィンドウは 640x400 の端末で 1MB。8 ビットのウィンドウは 8 ビットのまま持つ。画面の大きさはメモリに合わせて決める（§3.1）。8MB のシナリオ（`20-low-memory`）が 640x480 で通ることを確かめる
- **大きな画面の速さ**: 1920x1200 の画面全体は 9.2MB。メモリの多い機械は CPU も速いはずだが、書き換えた範囲だけ送ることがいっそう大事になる

### 3.9 フロッピーの空き

- 圧縮したイメージの空きは約 865KB で、フォント・アイコン・アプリの増加分は入る見込み
- 圧縮しないイメージ（`COMPRESS=0`）の空きは 22KB しか無いので、フォントとアイコンは `COMPRESS` に関係なくいつも gzip で入れる（D-047。データであってカーネルやアプリではないので、`COMPRESS=0` の目的は保てる。展開はアプリと同じ `miniz_oxide`）
- それでも M4 で圧縮しないイメージに入らなくなったので、圧縮しないイメージに入れるアプリを減らした（`RAW_APPS`。オーナーの指示、D-050）

## 4. 段階（Phase）と完了条件

ブランチの上では Phase を `M1`〜`M6` と呼ぶ（main の Phase 番号とぶつからないように。§5）。

| 段階 | 内容 | 完了条件（自動で確かめる） |
|---|---|---|
| M1 | 32 ビットの画面: ローダのモードの選び方（32 ビットのみ・大きい順・メモリと EDID の上限・`video=`）・ブート情報・画面の大きさの決め打ちをやめる・32 ビットの重ね合わせ・8 ビットのウィンドウの表での変換。**見た目は変えない** | 今あるシナリオが全部、`video=640x480` の 32 ビットの画面で今の期待画像のまま通る（テストの既定を `video=640x480` にする）。EDID が無ければ 1024x768（`VGA.edid=off`）、EDID があればその大きさ（`VGA.xres`/`yres` で 1600x1200）。メモリで画面の大きさが抑えられる（`-m 8M` で 640x480、`-m 16M` で `video=1920x1200` でも 800x600）。`-m 128M` と `video=1920x1200` で 1920x1200 のデスクトップでアプリが動く。シリアルに `video limit: …`・`video: WxHx32`。32 ビットのモードを持たないカード（`-vga cirrus`）でレトロになる |
| M2 | `vibe-gfx` の `Canvas`: アルファ合成・角の丸い矩形・影・グラデーション・アルファ付きの画像・32 → 8 ビット | ホストのテストで各機能のピクセルが期待どおり。ktest で 1024x768 の重ね合わせの時間を測ってシリアルに出し、上限以内 |
| M3 | フォント: `vibe-fontgen`・`.VFN`・描画と `measure`・カーネルの読み込み・モダンの端末を固定幅のフォントに。**大きさの変わるもの**（バー・タイトルバー・メニュー・端末 80x25・ウィンドウの位置）とテストの画面を 1024x768 にすること（D-049 で M4 から移した） | ホストのテストで形式の往復と文字の幅・描いたピクセル。デスクトップのシナリオを 1024x768 の新しい期待画像で（目で確かめてから）。`.VFN` を消したイメージで 8x8 のまま起動する（`65-fonts-missing`）。ktest でフォントを読み込めた。レトロのシナリオは今の期待画像のまま |
| M4 | ウィンドウの見た目（座標の変わらないもの）: テーマ・角の丸いウィンドウと影・タイトルバーのアイコンのボタンとホバー・バー・メニュー・カーソル・グラデーションの背景・アイコン（`vibe-icongen`） | デスクトップのシナリオ（`46-desktop-bar` など）を新しい期待画像で。タイトルバーのボタンにマウスを乗せると色が変わる（画面の比較）。マウスだけで「メニュー → 起動 → 最小化 → 戻す」が今までどおりできる |
| M5 | 32 ビットのウィンドウ（`WIN_RGB32`）と `vibe-ui` の新しい見た目。`calc`・`files`（アイコン付き）・`tasks`・`clock`（なめらかな針）を移す | `vibe-ui` のホストのテストが通る（配置は変わってよい）。各アプリのシナリオを新しい期待画像で。8 ビットのままのアプリ（`mines` など）も今までどおり動く。レトロで `calc` が起動して動く |
| M6 | 残り: `mines`・`blocks`・`paint`・`view`（24 ビットの BMP をそのまま）・背景の 24 ビット BMP。ANSI の配色。（任意）`settings`（強調色・背景）・暗い配色 | 各アプリのシナリオ。`view` の 24 ビットの画像が誤差拡散されずに出る（画素の比較）。`make test` が全部通る |

- M1 は土台なので最初に行い、見た目を変えないことで「32 ビットの重ね合わせが正しい」ことを今の期待画像で確かめる
- M2・M3 は順番を入れ替えてよい。M4 は M2・M3 の後
- M3 以降は期待画像を作り直すことになる。新しい期待画像は必ず目で確かめてからコミットする（AGENTS.md）。作り直したものは LOG.md に一覧を残す
- レトロモードのシナリオ（`video=320x200` のもの）は、どの段階でも今の期待画像のまま通ることを確かめる

## 5. ブランチの進め方

- ブランチ `modern-look`（main の `3d4ca86` から）。main に合流するかは、M4 か M5 の後にスクリーンショットを見てオーナーが決める
- コミットは D-039 のとおり、計画書を順番に実行している間は段階ごとにコミットする。push はしない
- 文書（PLAN.md・LOG.md・DECISIONS.md・DESIGN.md）もこのブランチの上で更新する。PLAN.md には `M1`〜`M6` として載せる。DECISIONS.md の番号は D-046 から続けるが、main でも決定が増えていたら合流のときに振り直す
- main で作業が進んだら、段階を始める前に main をこのブランチに取り込む（merge。履歴は書き換えない）。取り込むかどうかと時期はオーナーに確認する
- このブランチがある間に main で `gui`・`vibe-ui`・`vibe-gfx`・アプリの描画を大きく変えると、合流のときにぶつかる。main で日本語の表示などを始めるなら、フォントの形式（§3.3）を先にどちらかで決めておく
- 合流しないと決めた場合も、ブランチは消さずに残す（実験の記録として）

## 6. オーナーに決めてほしいこと

D-047 で答えをもらった（見た目の方向・フォント・アイコン・クラシックの見た目・圧縮しないイメージは推奨のまま。モダンは 32 ビットだけ、画面は大きいモードを優先、メモリの多い機械ではもっと広い画面を使う）。残りは次の 2 つで、推奨のとおりに書いてある:

1. **画面の大きさの上限**: 推奨は「メモリ（画面 1 枚が RAM の 1/8 以下）とモニタ（EDID の本来の解像度。読めなければ 1024x768）の両方で決め、最大 2560x1600」（§3.1）。`video=` で指定もできる
2. **レトロモード（320x200）を残すこと**: 推奨は残す。今の全画面モードをそのまま使うので手間は小さい（8 ビットの出力・32 ビットのウィンドウの色の変換・8x8 のフォントを残すだけ）。486 の頃の実機はふつう 32 ビットの VESA モードを持たないので、残さないと実機で起動できなくなる

## 7. 心配な点

- **モニタ**: EDID を返さないモニタ・切り替え器もある。そのときは 1024x768 までにするが、それでも映らない古いモニタではレトロ（Shift）で逃げる
- **実機**: 486 の頃のビデオカードは VRAM が 1〜2MB で、32 ビットのモードはほぼ無い（640x480x32 でも 1.2MB 要る）。実機ではたいていレトロになる。モダンを実機で見るには、VESA 2.0 で 32 ビットのモードを持つ後の時代のカード（PCI）が要る。そういう機械でも ISA・VLB のカードでは VRAM への書き込みが遅く、画面全体の書き直しが目に見えて遅いおそれがある。QEMU の速さだけで判断しない
- **期待画像の作り直し**: 画面を比べるところは今 36 か所あり、そのうちデスクトップのものはほぼ全部作り直しになる（M4 で画面も 1024x768 に変わる）。1 枚ずつ目で確かめる手間が大きい。作り直す範囲を段階ごとに分ける（M1 では作り直さない）
- **シナリオの座標**: 画面の大きさが変わると、マウスの移動（相対）とウィンドウの位置が変わる。シナリオは画面の大きさを `video=` で固定して書く
- **フォントの見た目**: 4 ビットの濃さで小さな文字（11〜13 ピクセル）をなめらかにすると、にじんで見えることがある。ヒンティングはホストのツール任せになる。数種類の大きさを画像にしてオーナーに見てもらってから決める
- **カーネルスタック**: 32 ビットの行のバッファ（1024×4 = 4KB）や影の表をスタックに置かない（AGENTS.md の「大きな値をスタックに置かない」）。ヒープか静的な領域（初期値 0）に
- **Bochs・86Box**: Bochs の VBE は 32 ビットに対応しているが、画面の比較はしていない（今までどおり）。モダンで起動して DHCP・ping のシナリオが通ることだけ見る
- **main との分かれ**: ブランチが長く続くほど合流が難しくなる（§5）

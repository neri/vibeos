## 2026-10-11 設計

### 決めたこと
設計の議論を行い、DESIGN.md / PLAN.md / DECISIONS.md を作成した。決定の経緯は DECISIONS.md D-001〜D-017。流れ:
1. オーナーが前提（x86, フロッピーイメージ, QEMU, モード 13h）を提示 → AI が設計書ドラフトを作成（言語は C を推奨）
2. 実機を想定しない場合に何が変わるかを AI が説明
3. オーナーが方針を決定: 目的は「AI がどこまで作れるか」、言語は Rust、QEMU 専用にしない、日本語は見送り、キーボードは US
4. オーナーが 32bit と外部クレートの方針を決定
5. オーナーがマルチタスクの後付けを懸念 → スケジューラを Phase 5 に前倒し
6. オーナーの問いかけで、設計書を設計・計画・決定・経過に分割

### 環境の確認
- あり: `nasm`, `qemu-system-i386`（11.1.2, `~/opt/qemu-11.1.2`）, `mtools`, `mkfs.fat`, `clang`, `gcc`, `ld.lld`, `llvm-objcopy`, `gdb`, `make`
- Rust: stable 1.99.0, nightly 1.101.0（2026-10-09）, nightly に `rust-src` 導入済み
- 無し: `i686-elf-gcc`, `zig`, Bochs, 86Box
- `rustc --print target-list` に `i686-unknown-none` は無い（`x86_64-unknown-none` と `i686-unknown-uefi` はある）
- QEMU は `-cpu pentium2` に対応

### Rust の 32bit ベアメタル試作
スクラッチ領域で最小のカーネル（`_start` から `kmain` を呼び VRAM に書き込むだけ）をビルドした。
- `rustc +nightly -Z unstable-options --print target-spec-json --target i686-unknown-linux-gnu` の出力を元にカスタムターゲット JSON を作成
- **詰まった点 1**: `"rustc-abi": "x86-softfloat"` は拒否された。この nightly で使える値は `softfloat` / `x86-sse2` / `powerpc-spe` / `sparc-v8plus`。`softfloat` で通った → nightly の版を固定する理由になった
- ビルドは `-Zbuild-std=core,alloc,compiler_builtins -Zbuild-std-features=compiler-builtins-mem -Zjson-target-spec` で成功（約 9 秒）。`cpu` は `pentium4` と `i686` のどちらでも通った
- 出力は `ELF 32-bit LSB executable, Intel 80386`。逆アセンブルで VRAM（`0xa0000`）への書き込みループを確認
- **詰まった点 2**: `.eh_frame_hdr` / `.eh_frame` が `0x100000` に置かれ、`_start` が `0x100030` にずれた → リンカスクリプトで `.text.entry` を先頭に置き `.eh_frame*` を捨てる必要がある
- QEMU での起動は未確認（ローダがまだ無いため）

- Cargo ワークスペース: `kernel` と `tools/vibe-run`。ルートの `cargo build` / `cargo test` はホスト向けだけ（`default-members`）。カーネルは `kernel/` に入ってビルドし、`kernel/.cargo/config.toml` でターゲットと build-std を指定する

- ビルド時に core の SSE 関数について「将来エラーになる」警告が出る（soft-float ターゲットで `#[target_feature(enable = "sse")]` があるため）。カーネルからは使わないので当面無視
- テストランナー `tools/vibe-run` を作成: QEMU を画面なしで起動し、QMP（UNIX ソケット）で画面取得・キー入力、シリアル出力の待ち合わせ、終了コードの確認をシナリオファイル（`tests/scenarios/*.scn`）で行う。イメージは `snapshot=on` で開くのでテストで書き換わらない
- QEMU に `-nic none` を付けた（iPXE の ROM が読まれて起動が遅くなるのを防ぐ）
- `make test` で Phase 0 のシナリオ（QEMU が起動し QMP で操作できる）が通った


## 2026-10-11 Phase 1: IPL と 2nd ステージ

- `boot/boot.asm`（IPL）: BPB は mkfs.fat と同じ値。ディスクの形は実行時に BPB から読む。LBA 1〜63 をトラック単位でリトライ付きで読む
- `boot/loader.asm`: シリアル初期化 → A20 → unreal モード → E820 → モード 13h とバー → フロッピー全体を `0x400000` へ → FAT12 から `KERNEL.SYS` を `0x100000` へ → プロテクトモード → カーネルへ。決定の理由は DECISIONS.md D-018
- ブート情報構造体に `kernel_addr` / `kernel_size` を追加（物理メモリ管理でカーネル領域を予約するため）
- Makefile でイメージを組み立てた後に `fsck.fat -n` を実行し、BPB の不一致を検出できるようにした
- 一度で動いた。QEMU の E820 は 6 エントリ。ディスク 0x168000 バイト（1.44MB）を読み、空のカーネル（3 バイト）にジャンプするところまで確認
- QEMU の `screendump` はモード 13h を 2 倍の 640x400 で出力する。テストの座標はこの大きさで書く
- テスト `01-loader`: シリアルの各段階のメッセージと、バーの 2 点の色を確認
- 未確認: 実機・Bochs での起動

## 2026-10-11 Phase 2: Rust カーネルの起動

- `crates/vibe-font`（font8x8 のデータを包み、文字の大きさはフォントから取る）と `crates/vibe-gfx`（Surface への描画、標準パレット）を作成。ホストでテスト 13 件
  - Bresenham の直線のテストで期待値を間違えていた（傾き 0.5 では理想点がちょうど中間になり、実装の結果も正しい）。期待値の方を直した
- カーネル: `_start`（BSS ゼロクリア → 16KB のブートスタック → `kmain`）、ポート I/O、`IrqMutex`、シリアル（ループバックで UART の有無を確認）、VGA（裏画面 + 変更行だけ転送）、テキストコンソール（40×25）、パニック画面（赤背景）
- `IrqMutex` は単一 CPU 前提で「割り込み禁止 + 二重取得を検出したら panic」。panic 処理の中だけ `force_get` でロックを無視する
- ブートスタックを `static`（不変）にしていて、書き込むと未定義動作になるところだった。`static mut` にして `sym` で番地だけ渡す形に直した
- 画面テストで、カーネルの大きさなどビルドごとに変わる値が写ると毎回期待画像がずれる問題に気づき、vibe-run に範囲を指定した比較（`expect-screen NAME X Y W H`）を追加
- QEMU の E820: 6 エントリ、使用可能 32255KB（`-m 32M`）


## 2026-10-11 Phase 3: 割り込み・タイマ・キーボード

- GDT（カーネル/ユーザのコード・データ + TSS）、IDT（例外 0〜31, IRQ 0x20〜0x2F, システムコール 0x80）、共通の割り込み入口（`TrapFrame` に全レジスタを積む）、PIC の付け替え、PIT 100Hz、PS/2 キーボード、CPUID の確認、NMI の再有効化
- `crates/vibe-keyboard`: セット 1 のスキャンコード解釈と US 配列（ホストでテスト 9 件）
- `WaitQueue` の仮実装（`sti; hlt` で次の割り込みまで止まり、条件を見直す）。キー入力待ちと `sleep_ms` はこれを通す
- 仮のモニタ（`help` / `ticks` / `sleep` / `divzero` / `panic`）。Phase 7 でシェルに置き換える
- **詰まった点 1**: スキャンコード 0xAA を「キーボードの自己テスト応答」として捨てていたが、左 Shift を離したときのコードと同じだった。ホストのテストで見つかった。離しとして扱うよう修正
- **詰まった点 2**: キーを押すと「unexpected interrupt 204」。逆アセンブルすると、Intel 記法の `push ds` が 16bit の push（`66 1e`）になっていて、`TrapFrame` が 8 バイトずれていた。EAX 経由で 32bit で積むように修正（CLAUDE.md に注意を追記）
- **詰まった点 3**: 直しても今度はキー入力が届かない。タイマの割り込みで 8042 の状態と PIC のマスクを一時的にログに出したところ、PIC は正しく、8042 の出力バッファにデータが来ていなかった。原因は、ポート 1 を無効にした後に読んだ設定バイト（「ポート 1 のクロック無効」ビットが立っている）を、最後にそのまま書き戻していたこと。そのビットを落とすよう修正
- テスト: `03-keyboard`（入力・Shift・CapsLock・BackSpace・`sleep` の精度）, `04-divzero-panic`（#DE でパニック画面）
- 二重フォルト用の別スタック（タスクゲート）は未対応。スタックあふれはトリプルフォルトになり、`-no-reboot` で QEMU が止まる
- Bochs はインストールに sudo のパスワードが要るため未導入（オーナーに依頼する）

## 2026-10-11 Phase 4: メモリ管理

- `crates/vibe-alloc`: 物理ページのビットマップ（1 = 空きにして、静的変数でも BSS に入るようにした）と、ヒープの空きリスト（割り当て単位を管理情報の大きさにそろえ、分割の余りが必ず空きブロックとして持てるようにした）。ホストでテスト 11 件（ランダムな割り当て・解放 2 万回で上書きが無いこと、最後に 1 ブロックに戻ること）
  - ページアロケータの「探し始めの位置から後ろに無ければ先頭に戻る」テストで、`free` が探し始めの位置を戻すことを考慮しておらず、期待値が間違っていた。テストを直した
- カーネル: `mm::pmm`（E820 の 1MB〜1GB）、`mm::paging`（4KB ページ、0 番地は対応付けない、CR0.WP）、`mm::heap`（GlobalAlloc、足りなければ物理ページを追加）
- ページングの設計で、カーネル空間に後からページテーブルを足すとプロセスのページディレクトリ（カーネル部分をコピーして共有）に反映されない問題に気づき、カーネル空間のページテーブルは起動時に作ったものだけにした（`map` は RAM の外のカーネル空間を拒否する）
- カーネル内テストの仕組み: `qemu-test` 機能付きのカーネルでテスト用イメージを作り、`ktest` で 7 件（Vec / String / BTreeMap / ヒープの拡張 / 解放したメモリの再利用 / ページの割り当て / ページの対応付け）
- モニタに `mem` と `nullptr` を追加。`06-page-fault` で 0 番地の読み込みがページフォルト（cr2=0）になることを確認
- QEMU 32MB での状態: 管理ページ 30008KB、カーネルは 0x100000〜0x129220（BSS にビットマップ 32KB・裏画面 64KB・ブートスタック 16KB）

## 2026-10-11 Phase 5: スケジューラ

- `task::sched`: タスクごとに 16KB のカーネルスタック + ガードページ、`switch_context` での切り替え、ラウンドロビン（20ms）、タイマ割り込みからのプリエンプション、アイドルタスク、終了したタスクの回収、`join`
- `WaitQueue` を本実装に差し替え（待ち行列に入れて眠り、`notify_all` で起こす）。呼び出し側（キーボード・`sleep_ms`）は変更なし。Phase 3 から「待つ処理は必ず WaitQueue を通す」を守っていたので差し替えだけで済んだ
- 二重フォルト用の TSS とタスクゲート。モニタの `overflow`（無限再帰）でガードページ → 二重フォルト → パニック画面になることを確認
- `kmain` は初期化後にモニタを別タスクとして作り、自分は終了する（起動時のスタックにはガードページが無いので）
- **気づいた点**: データレイアウトが `S128`（関数の入口で ESP+4 が 16 の倍数）なのに、`_start` → `kmain`、割り込みの入口 → `dispatch`、新しいタスクの初期スタックでそろえていなかった。今は SSE を使わないので実害は出ていなかったが、そろえるように修正
- **詰まった点**: 「終わったタスクのスタックが回収される」テストが失敗。物理ページが 5 ページ（= スタック 1 つ分）合わなかったので最初は回収漏れを疑ったが、比較の左右を読み違えていた。実際は前のテストのタスクがまだ回収されておらず、基準値を測った後に回収されていた。基準値を測る前に `yield_now` で回収させるよう修正
- カーネル内テストは 13 件（スケジューラ関係 6 件: プリエンプション、WaitQueue、sleep の精度、アイドル中の hlt、切り替えの負荷、スタックの回収）。3 回続けて全部通ることを確認
- 観察: 休まないスレッド（T0）がいると、10ms 休むスレッドと 20ms 休むスレッドの進みが同じになる（起きても T0 の持ち時間 20ms が終わるまで待つため）。起きたタスクを優先する仕組みは必要になったら検討する
- モニタに `ps` / `demo`（3 つのスレッドが画面右上のカウンタを 5 秒間進める）/ `overflow` を追加

## 2026-10-11 Phase 6: ファイルシステム

- `crates/vibe-fat`: FAT12/16 の読み込み（BPB の検査、ルート・サブディレクトリ、クラスタの連鎖、オフセット付きの読み込み）。ホストでテスト 8 件（mkfs.fat / mmd / mcopy で作ったイメージ、FAT16 の 16MB イメージも）

- ディスクに入れるファイルを `rootfs/` に置き、Makefile が `mcopy -s` で入れる
- **詰まった点**: 起動直後にページフォルト（cr2=0x810）で全シナリオが失敗。0x810 = 0x500 + 0x310 でブート情報の `ramdisk_size`。Phase 4 で 0 番地のページ（0〜0xFFF）を対応付けないようにしたので、ページング後に 0x500 のブート情報が読めなくなっていた（それまではページング前にしか読んでいなかったので表に出なかった）。起動直後にカーネル内に写すよう修正
- シナリオ `09-files` の待ち方を、`ls` の表示順に合わせて修正（`wait-serial` は前に一致した位置より後ろを探す）
- モニタに `ls` / `cat` / `cd` / `pwd`。プロンプトにカレントディレクトリを表示
- カーネル内テスト 19 件（眠る Mutex、KERNEL.SYS の中身がローダの置いたものと一致、テキストファイル、エラー、少しずつ読む、カレントディレクトリがタスクごと）

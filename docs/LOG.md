## 2026-10-11 設計

### 決めたこと
設計の議論を行い、DESIGN.md / PLAN.md / DECISIONS.md を作成した。決定の経緯は DECISIONS.md D-001〜D-017。流れ:
1. オーナーが前提（x86, フロッピーイメージ, QEMU, モード 13h）を提示 → AI が設計書ドラフトを作成（言語は C を推奨）
2. 実機を想定しない場合に何が変わるかを AI が説明
3. オーナーが方針を決定: 目的は「AI がどこまで作れるか」、言語は Rust、QEMU 専用にしない、日本語は見送り、キーボードは US
4. オーナーが 32bit と外部クレートの方針を決定
5. オーナーがマルチタスクの後付けを懸念 → スケジューラを Phase 5 に前倒し
6. オーナーの問いかけで、設計書を設計・計画・決定・経過に分割

### 環境の確認

### Rust の 32bit ベアメタル試作
スクラッチ領域で最小のカーネル（`_start` から `kmain` を呼び VRAM に書き込むだけ）をビルドした。
- `rustc +nightly -Z unstable-options --print target-spec-json --target i686-unknown-linux-gnu` の出力を元にカスタムターゲット JSON を作成
- **詰まった点 1**: `"rustc-abi": "x86-softfloat"` は拒否された。この nightly で使える値は `softfloat` / `x86-sse2` / `powerpc-spe` / `sparc-v8plus`。`softfloat` で通った → nightly の版を固定する理由になった
- ビルドは `-Zbuild-std=core,alloc,compiler_builtins -Zbuild-std-features=compiler-builtins-mem -Zjson-target-spec` で成功（約 9 秒）。`cpu` は `pentium4` と `i686` のどちらでも通った
- 出力は `ELF 32-bit LSB executable, Intel 80386`。逆アセンブルで VRAM（`0xa0000`）への書き込みループを確認
- **詰まった点 2**: `.eh_frame_hdr` / `.eh_frame` が `0x100000` に置かれ、`_start` が `0x100030` にずれた → リンカスクリプトで `.text.entry` を先頭に置き `.eh_frame*` を捨てる必要がある
- QEMU での起動は未確認（ローダがまだ無いため）

## 2026-10-11 Phase 1: IPL と 2nd ステージ

- `boot/boot.asm`（IPL）: BPB は mkfs.fat と同じ値。ディスクの形は実行時に BPB から読む。LBA 1〜63 をトラック単位でリトライ付きで読む
- `boot/loader.asm`: シリアル初期化 → A20 → unreal モード → E820 → モード 13h とバー → フロッピー全体を `0x400000` へ → FAT12 から `KERNEL.SYS` を `0x100000` へ → プロテクトモード → カーネルへ。決定の理由は DECISIONS.md D-018
- ブート情報構造体に `kernel_addr` / `kernel_size` を追加（物理メモリ管理でカーネル領域を予約するため）
- Makefile でイメージを組み立てた後に `fsck.fat -n` を実行し、BPB の不一致を検出できるようにした
- 一度で動いた。QEMU の E820 は 6 エントリ。ディスク 0x168000 バイト（1.44MB）を読み、空のカーネル（3 バイト）にジャンプするところまで確認
- QEMU の `screendump` はモード 13h を 2 倍の 640x400 で出力する。テストの座標はこの大きさで書く
- テスト `01-loader`: シリアルの各段階のメッセージと、バーの 2 点の色を確認
- 未確認: 実機・Bochs での起動

- テスト: `03-keyboard`（入力・Shift・CapsLock・BackSpace・`sleep` の精度）, `04-divzero-panic`（#DE でパニック画面）

## 2026-10-11 Phase 5: スケジューラ

- `task::sched`: タスクごとに 16KB のカーネルスタック + ガードページ、`switch_context` での切り替え、ラウンドロビン（20ms）、タイマ割り込みからのプリエンプション、アイドルタスク、終了したタスクの回収、`join`
- `WaitQueue` を本実装に差し替え（待ち行列に入れて眠り、`notify_all` で起こす）。呼び出し側（キーボード・`sleep_ms`）は変更なし。Phase 3 から「待つ処理は必ず WaitQueue を通す」を守っていたので差し替えだけで済んだ
- 二重フォルト用の TSS とタスクゲート。モニタの `overflow`（無限再帰）でガードページ → 二重フォルト → パニック画面になることを確認
- `kmain` は初期化後にモニタを別タスクとして作り、自分は終了する（起動時のスタックにはガードページが無いので）
- **気づいた点**: データレイアウトが `S128`（関数の入口で ESP+4 が 16 の倍数）なのに、`_start` → `kmain`、割り込みの入口 → `dispatch`、新しいタスクの初期スタックでそろえていなかった。今は SSE を使わないので実害は出ていなかったが、そろえるように修正
- **詰まった点**: 「終わったタスクのスタックが回収される」テストが失敗。物理ページが 5 ページ（= スタック 1 つ分）合わなかったので最初は回収漏れを疑ったが、比較の左右を読み違えていた。実際は前のテストのタスクがまだ回収されておらず、基準値を測った後に回収されていた。基準値を測る前に `yield_now` で回収させるよう修正
- カーネル内テストは 13 件（スケジューラ関係 6 件: プリエンプション、WaitQueue、sleep の精度、アイドル中の hlt、切り替えの負荷、スタックの回収）。3 回続けて全部通ることを確認
- 観察: 休まないスレッド（T0）がいると、10ms 休むスレッドと 20ms 休むスレッドの進みが同じになる（起きても T0 の持ち時間 20ms が終わるまで待つため）。起きたタスクを優先する仕組みは必要になったら検討する
- モニタに `ps` / `demo`（3 つのスレッドが画面右上のカウンタを 5 秒間進める）/ `overflow` を追加

## 2026-10-11 Phase 8: マウス・画像・画面の切り替え

- PS/2 コントローラの初期化を `drivers/ps2.rs` にまとめ、2 ポート目（マウス）に対応。マウスの割り込みは生のバイトを積むだけで、`input` のマウス用スレッドがパケットを解釈（`vibe-keyboard::mouse`）してカーソルを動かし、アプリ向けのイベントを積む
- 画面を複数持てるようにした（0 番 = コンソール、アプリは全画面の画面を作って前面に出す）。マウスカーソルは VRAM に転送するときに重ねる
- BMP の読み込み（`vibe-gfx::bmp`、8/24/32 ビット）。8 ビットは画像のパレットをそのまま使い、24 ビットは誤差拡散で標準パレットに変換。最初は単純に近い色へ置き換えていたが、グラデーションの縞が目立ったので Floyd–Steinberg を入れた
- 自前で書いた（tinybmp は embedded-graphics の色の型を持ち込むため。無圧縮だけなら小さい）
- テスト用の画像はビルド時に `tools/mkassets`（Rust のホスト側ツール）で生成してディスクに入れる（リポジトリに画像ファイルを置かない）
- 組み込みアプリ `view` と `paint`。vibe-run に `mouse-move` / `mouse-button`（QMP の input-send-event）を追加
- **気づいた点**: `Screen` の静的変数に 0 でない初期値（カーソルの位置など）を入れたら、64KB の裏バッファごと `.data` に入ってカーネルが 64KB 大きくなっていた。初期値はすべて 0 にして `init` で設定する形に直した（CLAUDE.md に注意を追記）
- シナリオの待ち順の間違い（ps2 のログは READY より前）をまた起こした。CLAUDE.md に注意を追記
- テスト: `12-view`（8 ビットと 24 ビットを期待画像で比較、戻るとパレットが標準に戻る、BMP でないファイル）, `13-paint`（マウスの移動量が 1:1 で線になる、色の選択）
- QEMU の画面取得では、パレットの 63 は 255、42 は 168 になる

- Makefile がアプリをビルドし、デバッグ情報を除いて `/BIN` に入れる（hello 12KB, fault 20KB）
- **詰まった点 1**: アプリのシステムコールで「esi is used internally by LLVM」。EBX と ESI はインラインアセンブラの引数にできないので、値をメモリに置いて番地を渡す形にした
- **詰まった点 2**: それでも hello が 0 番地へのアクセスで止まった（ただしカーネルは落ちず、プロセスだけが止まりシェルに戻った = 保護が効いていることは確認できた）。逆アセンブルすると、番地を渡す `in(reg)` に ESI が割り当てられ、`mov esi, [esi+4]` で番地を壊していた。番地を EAX で渡すよう修正
- **詰まった点 3**: プロセスを 10 回動かすと物理ページが 190 ページ減る（カーネル内テストで発見）。`exit` システムコールは戻らないのに、システムコールの処理の中でプロセスへの `Arc` を持ったまま呼んでいたため、アドレス空間が解放されなかった。`exit` は `Arc` を取る前に処理するよう修正。同じ理由で、例外で止めるときの名前の `String` と、タスクの始まりで渡すクロージャの Box もリークしていたので直した（ユーザタスクは関数ではなく「入口とスタック」で始める形に）
- Ctrl+C で前面のプロセスを止める仕組みを追加（無限ループのアプリでシェルが戻らなくなるため）
- テスト: `14-user-process`（引数・ヒープ・終了コード・存在しないコマンド）, `15-user-faults`（0 番地・カーネルのメモリ・特権命令・0 除算・ユーザスタックあふれ・不正なポインタ・未定義のシステムコール・Ctrl+C）, カーネル内テスト 3 件（終了コード、起動できないファイル、プロセス 10 回でページが減らない）
